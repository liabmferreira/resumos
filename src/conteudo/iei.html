Setup do ambiente: SO, sistemas de ficheiros e as 3 formas de ter Linux

Objetivo da aula 0: todos com o mesmo ambiente (Linux + linha de comandos), para evitar o clássico “mas na minha máquina funciona!”.

Sistema Operativo (SO)

É o gestor dos recursos do computador: o software que executa tudo o resto. Gere o CPU (o cérebro), a memória (espaço de trabalho) e o armazenamento (o arquivo), e fornece uma interface de utilizador (UI).

Duas famílias em foco: Windows (o SO de desktop mais comum) e Linux (open-source, dominante em servidores, cloud e investigação científica).

Sistema de ficheiros (filesystem)

É o “catálogo da biblioteca” do computador: a forma como o SO organiza, armazena e encontra os ficheiros.

Windows (NTFS)

  • Usa letras de unidade (C:, D:).
  • Separador: barra invertida \.
  • Ex.: C:\Users\OSeuNome\Documents\OmeuFicheiro.txt

Linux (ext4, Btrfs, …)

  • Uma única raiz /, unificada.
  • Tudo é um ficheiro, incluindo dispositivos.
  • Separador: barra /.
  • Ex.: /home/oseunome/documents/omeuficheiro.txt
Porquê padronizar em Linux?
  • Padrão da indústria: base da web, da cloud (AWS, Google Cloud) e da computação científica.
  • Ferramentas poderosas para programação, automação e manipulação de dados.
  • Transparente: ajuda a perceber o que o computador está realmente a fazer.

Rede na VM: NAT

O hypervisor cria um adaptador de rede virtual. Normalmente usa NAT (Network Address Translation): funciona como um router e a VM partilha, de forma segura, a ligação à internet do anfitrião. É o que permite apt install e git dentro da VM.

WSL: rede e ficheiros

Rede: partilha automaticamente a ligação do Windows.

Ficheiros: as unidades Windows são montadas em /mnt/. C:\Users\OSeuNome fica em /mnt/c/Users/OSeuNome.

Armadilha (WSL)

Para melhor desempenho, trabalhar dentro do filesystem Linux (/home/utilizador/) e não em /mnt/c/.

O que costuma sair
  • Qual a opção mais segura / recomendada? VM. Melhor desempenho? Nativa (WSL quase nativo). Mais integrada com Windows? WSL.
  • Porque é que a VM tem internet? NAT do hypervisor.
  • Onde está o C: dentro do WSL? /mnt/c.
  • Passo crítico do dual-boot? Particionar (fazer backup antes).

Linux: terminal, shell e sistema de ficheiros

Terminal vs shell

O terminal é a janela; a shell é o “cérebro” lá dentro: o programa que interpreta os comandos.

Shells: sh (Bourne Shell, a original), zsh (moderna, muito personalizável), fish (fácil de usar), bash (Bourne Again SHell, a mais comum em Linux, padrão de facto).

Porquê a CLI? Poder e velocidade, automação (scripts), eficiência (poucos recursos), padrão da indústria. Analogia: GUI = menu do restaurante; CLI = falar diretamente com o chef.

Não confundir

/ = raiz do sistema de ficheiros. /root = pasta pessoal do utilizador root. São coisas diferentes.

Ficheiros ocultos

Em Linux, um ficheiro é oculto por convenção de nome: começa por ponto (.). Ex.: ~/.bashrc (configuração do bash, crucial), ~/.config (configurações de aplicações), ~/.themes ou ~/.local/share/themes (temas), ~/.gitconfig (configuração do Git).

~ = a tua diretoria pessoal ($HOME).

Caminhos absolutos vs relativos

Absoluto: começa em / e funciona de qualquer lado (cd /var/log). Relativo: parte da diretoria atual (cd Documents). Atalhos: . = diretoria atual, .. = diretoria pai, ~ = pessoal.

Linux: utilizadores, permissões e gestor de pacotes

Utilizador padrão vs superutilizador

Linux é multiutilizador. O utilizador padrão (ex.: student) tem privilégios limitados. O root é o administrador, com poder total.

sudo (Superuser do) executa um único comando com privilégios de root: sudo apt update. Pede a tua password.

ComandoO que faz

Permissões

ls -l mostra uma cadeia de 10 caracteres, ex.: -rwxr-xr--. Lê-se: tipo | dono (u) | grupo (g) | outros (o).

LetraNum ficheiroValor octal
r readler o conteúdo4
w writemodificar2
x executecorrer como programa1
-permissão ausente0
 
-  rwx  r-x  r--
│   │    │    └─ outros (o): só ler           → 4
│   │    └────── grupo  (g): ler e executar   → 4+1 = 5
│   └─────────── dono   (u): tudo             → 4+2+1 = 7
└─────────────── tipo: - ficheiro, d diretoria
chmod (change mode)

Modo simbólico (o dos slides): quem (u, g, o, a=todos) + +/- + r/w/x.

  • chmod u+x o_meu_script.sh: dá execução ao dono.
  • chmod +x ola.sh: dá execução a todos (forma usada nos scripts).
  • chmod o-w f.txt: tira escrita aos outros.

Modo octal (complemento, muito comum): um dígito por grupo, soma de r=4, w=2, x=1.

  • chmod 754 s.sh → -rwxr-xr--
  • chmod 644 f.txt → -rw-r--r-- (típico de ficheiro de texto)
  • chmod 755 dir → drwxr-xr-x (típico de diretorias/scripts)

Gestor de pacotes (APT)

Gestor de pacotes

Ferramenta que automatiza instalar, atualizar e remover software. Resolve dependências automaticamente e mantém uma base de dados do que está instalado. Em Debian/Ubuntu é o APT (Advanced Package Tool). Analogia: uma “App Store” do terminal.

ComandoO que fazsudo?
sudo apt updateSincroniza a lista de pacotes com os repositórios. Não atualiza software.Sim
apt search htopProcura nos nomes e descrições dos pacotesNão
sudo apt install htopDescarrega e instala o pacote e as dependênciasSim
sudo apt remove htopDesinstala mas mantém os ficheiros de configuraçãoSim
sudo apt purge htopDesinstala e apaga a configuraçãoSim
Armadilhas clássicas
  • apt update ≠ atualizar programas: só atualiza a lista do que existe. (Atualizar o software instalado é sudo apt upgrade, fora dos slides.)
  • Correr apt install sem sudo dá erro de permissão.
  • remove vs purge: só o purge apaga a configuração.
  • sudo é para um comando; não abras sessões como root sem necessidade.

cron e crontab

cron

O cron é um daemon (processo em background) que executa tarefas agendadas, os cron jobs. Cada utilizador gere os seus com o comando crontab. Usos: backups todas as noites, manutenção (ZFS scrub semanal, SSD trim diário), limpar temporários.

│ │ │ │ ┌───── dia da semana (0-6, 0 = Domingo)

* = “todos”. */15 no campo minuto = de 15 em 15 minutos. Ferramenta útil: crontab.guru.

Pipe de texto vs pipe de objetos

No CMD (e em bash) o pipe passa texto, que se filtra por padrões. No PowerShell passa objetos estruturados com propriedades, que se filtram e selecionam pelo nome.

REM CMD: filtra linhas de texto
tasklist | findstr /i "explorer"

# PowerShell: filtra objetos por propriedade
Get-Process | Where-Object { $_.ProcessName -eq "explorer" }
Get-Process "explorer" | Select-Object Name, CPU

$_ = o objeto atual no pipe. Where-Object filtra; Select-Object escolhe propriedades.

Virtualização: ideia central e os 3 tipos

Virtualizar é correr um computador dentro de outro. A Máquina Virtual (VM) é uma aplicação no PC físico, mas comporta-se como uma máquina separada.

Os 3 papéis
  • Anfitrião (Host): a máquina física e o seu SO.
  • Convidado (Guest): a VM e o SO que ela corre.
  • Hipervisor: o software que cria e gere as VMs.
O problema que o hipervisor resolveUma aplicação normal não acede ao hardware: pede ao SO. Mas o SO convidado espera controlo total. O trabalho do hipervisor é intercetar e gerir as instruções privilegiadas do convidado. A forma como o faz distingue emulação, virtualização completa e paravirtualização.

Emulação

Software imita o hardware de um sistema diferente. O emulador traduz cada instrução da CPU do convidado para a CPU do anfitrião (ex.: Dolphin/Yuzu correm jogos de GameCube/PowerPC ou Switch/ARM num PC x86).

  • + Corre software de outra arquitetura (ARM em x86).
  • − Muito lenta e gasta muita CPU (tradução instrução a instrução).

Virtualização completa

Corre um SO não modificado, da mesma arquitetura do anfitrião, com assistência de hardware da CPU (Intel VT-x / AMD-V). O convidado não sabe que é VM. Instruções normais correm diretamente na CPU; as privilegiadas são apanhadas pelo hardware (trap) e entregues ao hipervisor (“trap & emulate”). Ex.: Windows 11 no VirtualBox num Mac.

  • + Qualquer SO sem modificações; bom desempenho; forte isolamento.
  • − Sobrecarga dos traps, sobretudo em I/O intensivo.

Paravirtualização

O SO convidado sabe que é VM e tem drivers especiais. Em vez de provocar traps, faz hypercalls (chamadas diretas ao hipervisor). Base da cloud: instâncias AWS EC2 usam drivers VirtIO para disco e rede.

  • + Melhor desempenho (disco e rede), menos CPU.
  • − Exige SO modificado / com drivers (Linux e Windows modernos já os trazem).

Dispositivos, rede e passthrough

I/O: o hipervisor fornece dispositivos virtuais.

  • Emulado (ex.: placa Intel E1000): compatível mas lento.
  • VirtIO (paravirtualizado): canal eficiente para disco e rede. Rápido.

Rede virtual

  • NAT (padrão): VM partilha o IP do anfitrião. Acede à internet, mas é difícil a outros dispositivos ligarem-se a ela.
  • Bridge: VM tem IP próprio na LAN, parece um dispositivo físico. Ideal para servidores.
  • Passthrough USB: VM controla um dispositivo USB (ex.: programar Arduino/ESP32 a partir de uma VM Debian).
  • Passthrough PCI: dá uma GPU física à VM → desempenho quase nativo (jogos, ML). Exige IOMMU (Intel VT-d, AMD AMD-Vi), que isola a memória do dispositivo à VM atribuída.
Não confundirVT-x/AMD-V = virtualização da CPU. VT-d/AMD-Vi = IOMMU, para passthrough PCI.

Ideia-chaveContentores são processos isolados que partilham o kernel do anfitrião. Por isso correm à velocidade nativa e arrancam em segundos.

Camadas, volumes e rede

  • Camadas: a imagem é uma pilha de camadas só de leitura; cada instrução do Dockerfile cria uma camada. Builds rápidos (cache) e menos disco (imagens partilham camadas base).
  • Volumes: o sistema de ficheiros do contentor é efémero. Para persistir dados, um volume mapeia uma pasta do contentor para uma pasta do anfitrião.
  • Rede: o motor cria uma rede virtual em modo bridge; contentores na mesma rede têm IP privado e falam entre si.
  • Mapeamento de portas: -p 8080:80 = porta 8080 do anfitrião → porta 80 do contentor.
  • DNS interno (Compose): cada serviço chega a outro pelo nome do serviço (ex.: http://database).
Ordem das portasANFITRIÃO:CONTENTOR. Em -p 8080:80 abres localhost:8080 no browser; o serviço escuta na 80 dentro do contentor.

Branches, merge, conflitos, rebase e tags

BranchPonteiro leve e móvel para um commit. O principal chama-se main (antes master). Serve para trabalhar numa funcionalidade ou bug em isolamento, sem estragar o código estável.
ComandoEfeito
git branch <nome>Cria um branch (não muda para ele)
git checkout <nome>Muda o working directory para esse branch
git checkout -b <nome>Cria e muda num só passo
git logHistórico completo (autor, data, mensagem)

Merge

$ git checkout main            # 1. ir para o branch que vais ATUALIZAR
$ git merge feature/login      # 2. trazer o trabalho do outro branch

O Git cria um merge commit que une os dois históricos. (Se o main não avançou entretanto, o Git faz só fast-forward: move o ponteiro, sem merge commit — verificado na prática.)

Conflitos de merge

Acontecem quando os dois branches alteraram a mesma linha do mesmo ficheiro. O Git para e pede resolução manual. O ficheiro fica assim:

<<<<<<< HEAD
versão do branch atual (main)
=======
versão do branch que estás a juntar
>>>>>>> feature/login
Resolver um conflito
  1. git status → mostra os ficheiros em conflito (“both modified”).
  2. Abrir o ficheiro, escolher/combinar o código certo e apagar os marcadores <<<<<<<, =======, >>>>>>>.
  3. git add ficheiro → marca como resolvido.
  4. git commit → finaliza o merge.
ArmadilhaFazer commit com os marcadores ainda no ficheiro “resolve” o conflito para o Git, mas deixa o código partido. Testa antes do git add.

Rebase

Alternativa ao merge: reescreve o histórico. Pega nos commits do teu branch e reaplica-os, um a um, por cima do main mais recente → histórico linear, sem merge commit.

RegraNunca fazer rebase de branches públicos que outros colegas estejam a usar.

Tags e Releases

  • Tag (git tag v1.0.0): ponteiro permanente para um commit (ao contrário do branch, não se move). “Âncora” no histórico.
  • GitHub Release: página construída sobre uma tag: notas de lançamento (changelog), binários anexados (.exe, .zip), marcar como pré-lançamento.
O que costuma sairBranch vs tag (móvel vs fixo); qual comando cria e muda de branch (checkout -b); em que branch estar antes do merge (no que recebe); quando há conflito (mesma linha, mesmo ficheiro); perigo do rebase.

Remotes, GitHub, fork e Pull Requests

Remote e originRemote: ligação com nome a um repositório noutro local (servidor). origin: nome convencional do remote principal (de onde clonaste / para onde envias).
Git vs GitHubGit = a ferramenta (VCS distribuído, linha de comandos, local). GitHub = serviço web (2008, Microsoft) que aloja repositórios Git e junta uma camada social: issues, wikis, Pull Requests, Releases.

Fork e Pull Request

  • Fork: cópia pessoal, do lado do servidor, do repositório de outra pessoa, na tua conta GitHub. Primeiro passo para contribuir num projeto onde não podes fazer push.
  • Pull Request (PR): pedido formal para o dono do projeto “puxar” (merge) as tuas alterações (do teu branch ou fork) para o main dele. É uma página web e uma conversa: descrição do porquê, code review linha a linha, discussão, testes automáticos, aprovação e merge.
Não confundirFork ≠ clone. Fork é no servidor (GitHub); clone é a cópia no teu PC. PR não é um comando Git: é uma funcionalidade do GitHub.

Os dois endereços: MAC e IP

Endereço MAC (físico)48 bits, ex.: 00:1A:2B:3C:4D:5E. Gravado na placa de rede pelo fabricante, é permanente. Serve para comunicar dentro da mesma LAN. Analogia: número do passaporte.
Endereço IP (lógico)32 bits (IPv4) ou 128 bits (IPv6), ex.: 192.168.1.10. Atribuído pela rede (ex.: pelo router), é temporário. Serve para comunicar entre redes (WAN/Internet). Analogia: morada de casa.

ARP – descobrir o MAC a partir do IP

O PC 192.168.1.10 quer falar com a impressora 192.168.1.15 na mesma LAN. O switch só entende MAC. Então:

  1. O PC faz broadcast ARP: "Quem tem o 192.168.1.15?"
  2. A impressora responde: "Sou eu, o meu MAC é 00:AB:CD:EF:12:34."
  3. O PC guarda o par IP → MAC na sua tabela ARP e envia o pacote.

IPv4, máscara de sub-rede e cálculo de sub-redes

Um IPv4 vem sempre com uma máscara de sub-rede. A máscara divide o IP em parte de rede ("em que rua estou?") e parte de host ("qual o número da porta?"). É assim que o PC sabe se o destino é local (mesma rede, entrega direta) ou remoto (envia para o gateway).

Método: rede, broadcast e n.º de hosts
  1. Hosts = 2(32 − prefixo) − 2 (tira-se o endereço de rede e o de broadcast).
  2. Encontra o octeto "interessante" (onde a máscara não é 255 nem 0).
  3. Bloco = 256 − valor da máscara nesse octeto.
  4. Rede = maior múltiplo do bloco ≤ valor do IP nesse octeto; octetos seguintes a 0.
  5. Broadcast = rede + bloco − 1 nesse octeto; octetos seguintes a 255.
  6. Gama de hosts: rede + 1 … broadcast − 1.
Exemplo 1 – 192.168.10.77/26 Máscara 255.255.255.192 → octeto interessante é o 4.º. Bloco = 256 − 192 = 64. Múltiplos de 64: 0, 64, 128… → 77 cai no bloco 64.
Rede 192.168.10.64 · Broadcast 192.168.10.127 · Hosts .65 a .126 · 26 − 2 = 62 hosts.
Exemplo 2 – 172.16.5.200/20 Máscara 255.255.240.0 → octeto interessante é o 3.º. Bloco = 256 − 240 = 16. 5 cai no bloco 0 (0–15).
Rede 172.16.0.0 · Broadcast 172.16.15.255 · Hosts 172.16.0.1 a 172.16.15.254 · 212 − 2 = 4094 hosts.
Exemplo 3 – estão na mesma rede? 192.168.1.10/24 e 192.168.2.10/24: com /24 a rede são os 3 primeiros octetos → 192.168.1 ≠ 192.168.2 → redes diferentes. Têm de passar pelo router (gateway).

IPv6

O IPv4 esgotou-se. O IPv6 usa 128 bits (ex.: 2001:0db8:85a3::8a2e:0370:7334) e dá endereços praticamente ilimitados.

  • Loopback: ::1 (equivale a 127.0.0.1).
  • Link-local: fe80::… – automático, só para a LAN.
  • Unique local: fd00::… – equivale às gamas privadas do IPv4.

Gateway, routing, NAT, DNS e DHCP

Default gateway

O PC 192.168.1.10/24 quer falar com 8.8.8.8. Olha para a máscara e vê que o destino não está na rede local. Então envia o pacote para o default gateway: o IP do router na LAN (ex.: 192.168.1.1). É a "porta" para fora.

Routing (encaminhamento): encontrar o melhor caminho entre origem e destino, saltando por muitos routers da WAN (a Internet é uma rede de redes).

NAT – o "rececionista"Network Address Translation. Uma rede privada inteira (ex.: 50 dispositivos 192.168.1.x) "esconde-se" atrás de um único IP público. O router regista os pedidos que saem e devolve as respostas ao dispositivo certo. É a solução para a escassez de IPv4.
DNS – a "lista telefónica"Domain Name System. Sistema global e distribuído que traduz nomes (google.com) em IPs (142.250.184.142).
  • mDNS: DNS local sem servidor (meu-portatil.local, impressoras). DDNS: atualiza o nome de domínio quando o IP público de casa muda (servidor em casa).
  • NTP: sincroniza relógios (certificados, logs). SNMP: monitorizar routers, switches e servidores.

DHCP – IP automático

Configurar IP estático em cada dispositivo seria um pesadelo. O DHCP (Dynamic Host Configuration Protocol) faz isso automaticamente. Troca de 4 mensagens (DORA):

  1. Discover – o dispositivo "grita" (broadcast): "Há algum servidor DHCP? Preciso de IP!"
  2. Offer – o servidor (normalmente o router): "Podes usar o 192.168.1.50."
  3. Request – o dispositivo aceita.
  4. ACK – o servidor confirma.
  • Concessão (lease): o IP é "alugado" por um tempo (ex.: 24 h) e tem de ser renovado. IPs de quem sai voltam à pool.
  • Pool: gama gerida pelo servidor (ex.: .100 a .200).
  • Atribuição estática: IPs fora da pool (ex.: .1 a .99) ficam para servidores, impressoras e o router, que nunca devem mudar de IP.
Onde se configura a redeWindows: Painel de Controlo / Definições. Linux desktop: NetworkManager (ícone de rede). Linux servidor: systemd-networkd, ficheiros em /etc/systemd/network/.
ArmadilhaSe um PC tem IP 169.254.x.x (APIPA) ou nenhum IP, o DHCP falhou. Se faz ping 8.8.8.8 mas não ping google.com, o problema é DNS, não a ligação.
O que costuma sairPara que serve o gateway / NAT / DNS / DHCP; ordem das mensagens DHCP; porque é que servidores e impressoras têm IP estático.

Servidor e cliente TCP (eco)

# tcp_server.py
import socket
HOST = '127.0.0.1'
PORT = 65432
with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
    s.bind((HOST, PORT))
    s.listen()
    conn, addr = s.accept()          # bloqueia até um cliente ligar
    with conn:
        print(f"Ligado por {addr}")
        while True:
            data = conn.recv(1024)   # até 1024 bytes
            if not data:
                break                # cliente fechou
            conn.sendall(data)       # eco
# tcp_client.py
import socket
HOST = '127.0.0.1'
PORT = 65432
with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
    s.connect((HOST, PORT))          # handshake SYN/SYN-ACK/ACK
    s.sendall(b'Ola, mundo')         # envia bytes
    data = s.recv(1024)
    print(f"Eco recebido: {data.decode()}")

Servidor e cliente UDP (eco)

# udp_server.py
import socket
HOST = '127.0.0.1'
PORT = 65433
with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as s:
    s.bind((HOST, PORT))             # UDP: sem listen/accept
    data, addr = s.recvfrom(1024)    # dados + endereço do remetente
    print(f"Recebido {data.decode()} de {addr}")
    s.sendto(data, addr)             # responde a quem enviou
# udp_client.py
import socket
HOST = '127.0.0.1'
PORT = 65433
with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as s:
    s.sendto(b'Ola, UDP!', (HOST, PORT))   # sem connect
    data, addr = s.recvfrom(1024)
    print(f"Eco recebido: {data.decode()} de {addr}")
Sequência de chamadas (decorar) Servidor TCP: socket → bind → listen → accept → recv/sendall → close.
Cliente TCP: socket → connect → sendall/recv → close.
UDP: socket → (bind no servidor) → sendto/recvfrom. Não há listen, accept nem connect.
Armadilhas
  • Os sockets enviam bytes: b'...' ou .encode(); ao receber, .decode().
  • Em TCP o servidor usa o novo socket conn devolvido por accept(), não o s.
  • recv() devolve b'' quando o cliente fecha → sair do ciclo.
  • Correr o servidor antes do cliente; senão "Connection refused".

I/O blocante vs assíncrono

accept() e recv() bloqueiam: enquanto se atende um cliente, os outros esperam.

  • Multi-threading (thread por cliente): complexo (locks, race conditions), gasta recursos, e o GIL do CPython impede paralelismo real.
  • asyncio: uma thread, um event loop, muitas ligações; async/await pausam a função enquanto espera. Concorrência, não paralelismo. (asyncio.start_server para TCP, create_datagram_endpoint para UDP.)

REST, JSON, WebSockets, MQTT e brokers

APIs REST

Sockets são de baixo nível. A maioria dos serviços web expõe uma API. REST é um estilo arquitetural (conjunto de regras, não um protocolo) construído sobre HTTP (que corre sobre TCP).

  • Stateless: cada pedido leva toda a informação necessária.
  • Recursos: entidades identificadas por URL (/users, /products/123).
  • Verbos: métodos HTTP – GET (ler), POST (criar), PUT (atualizar/substituir), DELETE (apagar).
  • Dados: normalmente JSON.
GET /users/42        →  200 OK       { "name": "Alice", ... }
POST /users  {...}   →  201 Created
JSONJavaScript Object Notation: leve, legível, fácil de gerar e processar. Objetos { "chave": valor }, listas [ ], strings, números, true/false, null.
# main.py  –  correr com: uvicorn main:app --reload
from fastapi import FastAPI
app = FastAPI()
items = {1: {"name": "Laptop", "price": 1200}, 2: {"name": "Mouse", "price": 50}}

@app.get("/items/{item_id}")

        return items[item_id]          # dict → JSON automaticamente

# browser: http://127.0.0.1:8000/items/1

Sockets vs REST: sockets são baixo nível, protocolo próprio, podem ter estado, dados em qualquer formato. REST é alto nível, HTTP padronizado, stateless, JSON. Fazer REST sobre sockets puros seria reinventar o HTTP.

WebSockets

HTTP é client-pull: o servidor não pode enviar nada sem pedido. Fazer polling ("há novidades?" a cada 2 s) é ineficiente. O WebSocket é uma ligação persistente e full-duplex: começa com um pedido HTTP com Upgrade: websocket, o servidor responde 101 Switching Protocols, e a partir daí ambos enviam mensagens quando querem (URLs ws:// / wss://). Usos: chat, cotações/resultados ao vivo, jogos multijogador, edição colaborativa.

MQTT (IoT) – publish/subscribe

  • Publisher publica num tópico (ex.: home/livingroom/temp); subscriber escuta tópicos; o broker recebe tudo e reencaminha. Clientes totalmente desacoplados.
  • Wildcards: + = um nível (building/+/room102/light); # = vários níveis (building/floor1/#).
  • QoS 0: no máximo uma vez (como UDP). QoS 1: pelo menos uma vez (pode duplicar). QoS 2: exatamente uma vez (mais lento).
  • LWT (Last Will & Testament): mensagem que o broker publica se o cliente cair (ex.: "offline").
  • Cabeçalho mínimo de 2 bytes; porta habitual 1883 (biblioteca Python paho-mqtt).

Outros padrões

RabbitMQ (broker, AMQP): servidor inteligente, clientes "burros"; Producer → Exchange → Queue → Consumer; filas persistentes. ZeroMQ: biblioteca sem broker (REQ/REP, PUB/SUB, PUSH/PULL), muito rápida, sem ponto único de falha.

Cenários (desenvolvimento)

Cenário A – Um PC do laboratório não abre sites. Faz ping ao gateway 192.168.1.1 com sucesso e ping 8.8.8.8 também responde, mas ping www.ua.pt dá "Name or service not known". O que se passa e o que fazes?

Problema: a ligação IP até à Internet funciona (gateway e 8.8.8.8 respondem). Falha só a tradução de nomes → problema de DNS.

Passos / comandos:

  1. dig www.ua.pt (ou nslookup www.ua.pt) – ver se há resposta e de que servidor DNS.
  2. dig @8.8.8.8 www.ua.pt – se funcionar com outro servidor, o DNS configurado está errado ou em baixo.
  3. Ver o servidor DNS configurado (/etc/resolv.conf, NetworkManager ou ipconfig /all no Windows); corrigir para o DNS fornecido pelo DHCP ou um público; renovar a concessão DHCP se o DNS veio mal.

Justificação: o DNS é a "lista telefónica": sem ele o browser não sabe o IP de www.ua.pt, mesmo com a rede a funcionar. O teste por IP (8.8.8.8) isola a camada de rede da resolução de nomes.

Variante: se o ping ao gateway falhasse, o problema seria local (cabo/Wi-Fi, IP/máscara errados, DHCP – ver se tem 169.254.x.x). Se o gateway respondesse e 8.8.8.8 não, usar traceroute 8.8.8.8 para ver onde para (router/NAT/operador).

Cenário B – Escreveste um servidor TCP em Python (porta 65432) num servidor da UA. No próprio servidor, o cliente funciona com 127.0.0.1. No teu portátil, com o IP do servidor, dá "Connection refused" ou "timed out". Explica as causas prováveis e como verificas.

Problema: o servidor só está acessível localmente. Causas: (1) fez bind em '127.0.0.1' (loopback = "só este computador"); (2) uma firewall bloqueia a porta; (3) o servidor não está a correr.

Passos / comandos:

  1. No servidor: ss -tlnp | grep 65432 – se aparecer 127.0.0.1:65432, só aceita ligações locais. Mudar para s.bind(('0.0.0.0', 65432)) (todas as interfaces) ou para o IP da interface.
  2. No portátil: ping IP_servidor (chego à máquina?) e nmap -p 65432 IP_servidor (porta aberta, fechada ou filtrada?).
  3. "Timed out"/filtrada → firewall (iptables/nftables): abrir a porta 65432/TCP.
  4. Alternativa segura sem abrir portas: túnel SSH, ssh -L 65432:localhost:65432 user@servidor, e o cliente liga a 127.0.0.1:65432 no portátil.

Justificação: uma ligação é IP + porta. 127.0.0.1 nunca sai da máquina. "Refused" indica que nada escuta nesse IP:porta; "timeout" indica normalmente que uma firewall descarta os pacotes.

Páginas estáticas e HTML5

Uma página estática é um ficheiro entregue ao browser exatamente como está guardado no servidor. Todos veem o mesmo conteúdo (como uma brochura). O servidor só tem de encontrar o ficheiro (ex.: about.html) e enviá-lo. Tecnologias: HTML (estrutura) + CSS (estilo).

HTML = HyperText Markup LanguageHyperText: texto com links para outras páginas. Markup: linguagem de marcação, não de programação – descreve a estrutura com tags; não "faz" coisas (não tem if, ciclos…).

CSS – Cascading Style Sheets

O CSS dá o estilo (a "pele") ao HTML (o "esqueleto"): cores, fontes, layout, espaçamento, animações. Separar HTML (conteúdo/estrutura) e CSS (apresentação) é a Separação de Preocupações.

Regra CSS

h1 {                  /* seletor */

  font-size: 24px;
}                     /* tudo junto = conjunto de regras (ruleset) */
SeletorExemploSeleciona
ElementopTodas as tags <p>
Classe.my-classTodas as tags com class="my-class"
ID#my-idA única tag com id="my-id"

A cascata – quem ganha num conflito

  1. Origem: o CSS do programador sobrepõe-se ao estilo padrão do browser.
  2. Especificidade: o mais específico ganha. #id > .classe > elemento. (Inline ainda ganha a todos.)
  3. Ordem: com a mesma especificidade, ganha o que aparece por último.
p { color: blue; }
p { color: red; }        /* ganha a blue: mesma especificidade, vem depois */
.my-p { color: green; }  /* num <p class="my-p"> ganha: classe > elemento */

Como o browser obtém uma página (HTTP)

Os passos (resumo dos 13 do slide)
  1. Escreves http://example.com. Procura o IP na cache do browser, depois do SO (ficheiro hosts), depois no resolvedor DNS (router ou 8.8.8.8).
  2. Handshake TCP (SYN, SYN-ACK, ACK) para esse IP na porta 80 (HTTP) ou 443 (HTTPS).
  3. Envia o pedido HTTP em texto.
  4. No servidor, o Docker passa a porta do host para o contentor; o Nginx procura em /usr/share/nginx/html (pasta do host montada por volume) e encontra index.html.
  5. Envia a resposta HTTP pela mesma ligação TCP.
  6. O browser faz parsing do HTML; por cada <link>, <img>, <script> faz novos pedidos HTTP.
  7. Com tudo obtido, renderiza ("pinta") a página.

Reverse proxy e CORS

Proxy direto (forward)Esconde o cliente. Tu → Proxy → Internet. O Google vê o IP do proxy. Uso: filtrar/monitorizar tráfego (escola, empresa).
Reverse proxyEsconde o(s) servidor(es). Internet → Reverse proxy → servidores da app. O cliente só conhece o IP do proxy. Padrão em todas as apps web modernas.

Um reverse proxy (ex.: Nginx) é um "polícia de trânsito" que dá:

  1. Roteamento de pedidos: / → frontend, /api/ → backend.
  2. Balanceamento de carga: distribui por várias cópias do backend.
  3. Terminação SSL: o proxy trata do HTTPS; atrás dele usa-se HTTP simples.
  4. Caching: guarda ficheiros estáticos e serve-os diretamente.

No docker-compose só o serviço proxy tem ports: "80:80" (única porta pública); frontend e backend não têm ports – ficam escondidos.

# nginx.conf
events {}
http {
  server {
    listen 80;
    location /api/ { proxy_pass http://backend:5000; }   # DNS interno do Docker
    location /     { proxy_pass http://frontend:3000; }
  }
}

Same-Origin Policy e CORS

A SOP (Política de Mesma Origem) é uma proteção dos browsers: um script só pode fazer pedidos à mesma origem de onde veio. Origem = protocolo + domínio + porta. Impede, por ex., que evil.com faça fetch() ao teu banco onde tens sessão iniciada.

ABMesma origem?
http://example.com:80https://example.com:443Não (protocolo)
http://site.comhttp://api.site.comNão (domínio)
http://localhost:3000http://localhost:5000Não (porta)
CORS – Cross-Origin Resource SharingMecanismo para relaxar a SOP. Não é uma definição do browser: são headers HTTP que o SERVIDOR envia a dizer que origens têm permissão.
1. Frontend (localhost:3000) faz fetch('http://localhost:5000/api/users')
2. Browser vê pedido cross-origin → envia preflight OPTIONS ao backend
3. Backend responde:
   HTTP/1.1 204 No Content
   Access-Control-Allow-Origin: http://localhost:3000
   Access-Control-Allow-Methods: GET, POST, OPTIONS
   Access-Control-Allow-Headers: Content-Type
4. Browser: "permissão concedida" → envia o GET real
ArmadilhaUm erro de CORS corrige-se no backend (ex.: app.use(cors()) no Express, CORSMiddleware no FastAPI), não no JavaScript do frontend. O curl funciona na mesma porque a SOP é imposta só pelo browser. Com reverse proxy (frontend e /api/ na mesma origem) o problema desaparece.

Sequencial vs orientado a eventos

Programa sequencial: linha a linha; em input() pára e espera. Numa UI isso congelava tudo. As interfaces usam programação orientada a eventos: inicializa, regista handlers, entra no event loop e fica à escuta. "Princípio de Hollywood": não nos ligue, nós ligamos-lhe.

Um clique: o browser cria um objeto Event (X/Y, botão…) e, se o elemento tem listener, a função vai para a stack.

Event loop

  1. Call stack executa código síncrono (LIFO).
  2. setTimeout/fetch são delegados às Web APIs do browser (threads C++).
  3. Quando terminam, o callback vai para a callback queue (fila).
  4. O loop só passa o 1.º item da fila para a stack quando a stack está vazia. Por isso setTimeout(fn, 0) não corre logo.

Cenários (desenvolvimento)

Cenário A – Queres publicar o teu site estático com o docker-compose do Nginx (ports: "8080:80", volumes: ./my-site:/usr/share/nginx/html:ro). Fazes docker compose up, abres http://localhost:8080 e o browser mostra 404 Not Found (ou 403). O que verificas e como resolves?

Problema: o Nginx está a correr e a responder (há código HTTP, logo a rede e a porta estão bem), mas não encontra o ficheiro que devia servir. 404/403 são erros do lado do cliente/recurso, não de ligação.

Passos / comandos:

  1. Confirmar que existe ./my-site/index.html (nome exato, minúsculas, extensão .html) na pasta ao lado do docker-compose.yml: ls my-site/.
  2. Ver o que o contentor vê: docker compose exec webserver ls /usr/share/nginx/html. Se estiver vazio, o caminho do volume está errado (ex.: ficheiros em ./site ou numa subpasta).
  3. Testar no terminal: curl -I http://localhost:8080/ e curl -I http://localhost:8080/index.html para ver o código de estado.
  4. docker compose logs webserver mostra o caminho que o Nginx tentou abrir. Corrigir e reiniciar (docker compose down / up). Se só o CSS/imagens dão 404, rever href/src.

Justificação: o Nginx serve ficheiros a partir de /usr/share/nginx/html, que é a pasta do host montada por volume. Para o pedido GET / procura index.html. Se o ficheiro não está lá (ou tem outro nome), responde 404 (ou 403 por não haver índice). Se o browser desse "connection refused", aí sim seria problema de porta/contentor parado (docker compose ps).

Cenário B – O frontend em http://localhost:8080 faz fetch('http://localhost:8000/api/items') a uma API FastAPI. Na consola do browser aparece "blocked by CORS policy". Um colega diz para trocar o URL por http://backend-api:8000. Explica o problema e a solução correta.

Problema: localhost:8080 e localhost:8000 são origens diferentes (porta diferente). A Same-Origin Policy do browser bloqueia a resposta porque o backend não envia headers CORS a autorizar a origem do frontend.

Passos:

  1. DevTools (F12 → Network): o preflight OPTIONS volta sem Access-Control-Allow-Origin.
  2. Corrigir no backend: app.add_middleware(CORSMiddleware, allow_origins=["http://localhost:8080"], allow_methods=["*"]) (em desenvolvimento pode ser ["*"]; em produção, a origem exata).
  3. Alternativa: pôr um reverse proxy Nginx a servir o frontend em / e a encaminhar /api/ para o backend – tudo fica na mesma origem e o CORS deixa de ser necessário.

Justificação: CORS são headers que o servidor envia; o frontend não o pode "desligar". A sugestão do colega está errada: o JavaScript corre no browser, na máquina do utilizador, onde o nome backend-api não existe (só é resolvido pelo DNS interno do Docker). O URL certo continua a ser http://localhost:8000, a porta exposta no host.

Outliers com IQR

Método1. Q1 = percentil 25; Q3 = percentil 75.
2. IQR = Q3 − Q1.
3. D é outlier se D < Q1 − 1,5×IQR ou D > Q3 + 1,5×IQR.
Q1 = df["age"].quantile(0.25)
Q3 = df["age"].quantile(0.75)
IQR = Q3 - Q1
df_clean = df[~((df["age"] < Q1 - 1.5*IQR) | (df["age"] > Q3 + 1.5*IQR))]
# ~ = negação: fica com o que NÃO é outlier
Exemplo (corrido em Pandas)Idades 20, 21, 22, 23, 25, 95 → Q1 = 21,25; Q3 = 24,5; IQR = 3,25. Limites: 21,25 − 4,875 = 16,375 e 24,5 + 4,875 = 29,375. Só o 95 é outlier.

Porquê documentos compilados?

  • Git: um .docx é XML comprimido (binário) → o Git vê-o como "blob" e não faz diff útil. Em .tex/.md vês alterações linha a linha, histórico de commits e podes usar branches.

Ética em informática

  • "Dinheiro é uma coisa, mas dados são poder."
  • Manipulação política: a Cambridge Analytica usou dados pessoais para micro-targeting de eleitores (ex.: Brexit).

  • Imperativo ético: atrás de cada data point há um ser humano com direitos fundamentais.

RGPD — Regulamento Geral sobre a Proteção de Dados

O que éRegulamento (UE) 2016/679 (GDPR em inglês). Filosofia: a privacidade é um direito humano fundamental, não um luxo. Âmbito: aplica-se a qualquer entidade que trate dados de residentes da UE, seja onde for que o tratamento ocorra (uma empresa nos EUA também está sujeita).

  • Em Portugal, a autoridade de controlo é a CNPD (Comissão Nacional de Proteção de Dados). Cada instituição tem um DPO (Data Protection Officer / Encarregado de Proteção de Dados).

Cenários

Cenário A — Uma startup lança uma app de fitness que, além dos treinos, recolhe em segundo plano a localização contínua e a lista de contactos, partilhando tudo com uma empresa de publicidade. No registo há uma única caixa já assinalada "Aceito os termos". O que está errado e o que deve ser feito?

Problemas:

  • Recolha oculta → viola licitude, lealdade e transparência.
  • Contactos e localização contínua não são precisos para treinos → viola a minimização.
  • Partilha com publicidade → viola a limitação da finalidade.
  • Caixa pré-assinalada e genérica → consentimento inválido (tem de ser livre, específico, informado e explícito).
  • Dados de saúde/fitness podem ser dados sensíveis (art. 9.º, fora dos slides).

O que fazer: parar a recolha não necessária; pedir consentimento separado por finalidade, desmarcado por defeito e revogável; política de privacidade clara; definições mais privadas por defeito (privacy by default); prazos de conservação e eliminação; encriptação; DPIA; documentar tudo (accountability); verificar a transferência para o parceiro (contrato controller–processor, decisão de adequação se estiver fora da UE).

Justificação: Princípios do RGPD (Reg. UE 2016/679), privacy by design & default. Sem isso arrisca coimas até 20 M€ / 4 % do volume de negócios (fora dos slides) e queixas à CNPD.

Cenário B — Descobres que uma base de dados de clientes (nomes, e-mails, passwords em texto simples) ficou exposta publicamente durante uma semana devido a um erro de configuração. És o developer responsável. O que fazes?

Problema: violação de dados pessoais; falha do princípio da integridade e confidencialidade (passwords em claro, sem encriptação).

O que fazer:

  1. Conter: fechar o acesso de imediato e preservar logs.
  2. Informar o responsável pelo tratamento (controller) e o DPO.
  3. Notificar a CNPD em 72 horas após ter conhecimento (art. 33.º, fora dos slides) e avisar os titulares, porque há risco elevado (art. 34.º): pedir que mudem a password.
  4. Corrigir: forçar reset de passwords, guardá-las com hash e salt, encriptar dados, rever configurações, aplicar privacy by design.
  5. Documentar o incidente e as medidas (accountability).

Justificação: esconder a fuga agrava a infração e prejudica os utilizadores (risco de roubo de identidade e fraude, como nos slides). Eticamente, por trás de cada registo há uma pessoa.

Cenário C — A tua empresa quer usar uma biblioteca GPLv3 encontrada no GitHub dentro de um produto de software fechado que vai ser vendido a clientes. Além disso, o produto inclui um módulo de IA que ordena candidatos a emprego. O que aconselhas?

Parte 1 — Licença (fora dos slides): a GPL é copyleft. Ao distribuir o produto (vender a clientes), a obra derivada teria de ser distribuída sob GPL e com o código-fonte. Isso choca com manter o produto fechado.

Opções: substituir por uma biblioteca de licença permissiva (MIT, Apache 2.0, BSD); negociar uma licença comercial com o autor (dupla licença); ou aceitar publicar o produto em GPL. Se fosse LGPL, podia ser ligada (link dinâmico) sem abrir o código do produto. Em qualquer caso, manter avisos de copyright.

Parte 2 — IA de recrutamento: pelo AI Act é risco elevado (emprego). Precisa de: dados de treino de qualidade e sem enviesamento (evitar discriminação); logging automático; documentação técnica; supervisão humana capaz de se sobrepor às decisões. Pelo RGPD: DPIA antes do lançamento, minimização, transparência para os candidatos (fora dos slides: direito a não ficar sujeito a decisões só automatizadas, art. 22.º).

Justificação: GPL obriga a partilhar o código em derivados distribuídos; AI Act classifica recrutamento como alto risco; RGPD exige DPIA em tratamentos de risco elevado.

Cenário D — Um investigador quer publicar um dataset de saúde "anónimo": tirou os nomes mas deixou código postal, data de nascimento, sexo e diagnóstico. Está bem?

Problema: isto não é anonimização. Com código postal + data de nascimento + sexo, cerca de 87 % das pessoas são identificáveis (identificação indireta). O caso Netflix Prize mostra que cruzar dados reidentifica pessoas.

O que fazer: generalizar ou remover os quase-identificadores (só ano de nascimento, região em vez de código postal); avaliar o risco de reidentificação; fazer DPIA (dados de saúde são de alto risco); se ainda for possível identificar, tratar como dados pessoais (pseudonimização + encriptação + acesso controlado) e ter base legal/consentimento.

Justificação: só dados verdadeiramente anonimizados saem do RGPD. "Assumam sempre que os dados podem ser reassociados."
