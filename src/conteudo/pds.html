1 · Clean code

Definição de trabalhoCódigo fácil de perceber, alterar e verificar por outro programador. Não quer dizer "esperto", curto ou perfeito. Código que funciona não é necessariamente bom código, seja escrito por pessoas ou por IA.
ElementoRegras
NomesRevelam a intenção, pesquisáveis, pronunciáveis; sem letras soltas (mapeamento mental). Métodos com verbos (postPayment, getX, isY); classes com substantivos (Customer, AddressParser), sem ruído (Manager, Data, Info)
FunçõesPequenas (raramente > 20 linhas), fazem uma coisa, um nível de abstração por função; poucos argumentos (0 é ideal, depois 1, 2); evitar argumentos de saída (report.appendFooter() em vez de appendFooter(report)); o chamador fica acima do chamado
ComentáriosExplicar o porquê quando o código não chega. Aceitáveis: legais, informativos, intenção, avisos, TODO, Javadoc. Inaceitáveis: redundantes, enganadores, histórico de versões, ruído, código comentado
ClassesPequenas, medidas em responsabilidades; nome descreve a responsabilidade (nome vago ⇒ demasiadas responsabilidades)
OutrasSubstituir números mágicos por constantes; encapsular condições (if (shouldBeDeleted(timer))); evitar condições negativas; preferir enum a constantes static final int
// Pior: o leitor tem de decifrar
List<int[]> getThem() {
    List<int[]> list1 = new ArrayList<>();
    for (int[] x : theList) if (x[0] == 4) list1.add(x);
    return list1;
}
// Melhor: a mesma computação, intenção visível
List<Cell> getFlaggedCells() {
    List<Cell> flagged = new ArrayList<>();
    for (Cell cell : gameBoard) if (cell.isFlagged()) flagged.add(cell);
    return flagged;
}

Lente de code review

  1. Percebo a intenção?
  2. As responsabilidades são coerentes?
  3. Há conhecimento duplicado?
  4. As dependências são necessárias?
  5. Até onde se propaga uma alteração provável?

Não contar "violações": explicar as consequências. Mais classes e mais abstração não é automaticamente melhor.

// OCP + DIP: nova forma de pagamento = nova classe, Checkout não muda
interface PaymentMethod { double fee(double amount); }
class CardPayment implements PaymentMethod { public double fee(double a) { return a * 0.02; } }
class MbWayPayment implements PaymentMethod { public double fee(double a) { return 0.10; } }

    Checkout(PaymentMethod payment) { this.payment = payment; }   // injeção de dependência

}

Um mesmo objeto, dois tipos: em Animal a = new Dog(); o tipo declarado (estático) decide que métodos se podem chamar (a.fetch() não compila) e o tipo dinâmico decide que implementação corre (a.sound() executa a de Dog).

3 · Desenho de software

O desenho liga os requisitos (o quê) à construção (o código). É heurístico, não determinístico (dois designers produzem soluções diferentes), emergente (iterativo e incremental) e um wicked problem (só fica bem definido ao resolvê-lo).

Complexidade

Essencial: inerente ao problema. Acidental: criada pela solução. Objetivo: gerir a essencial sem acrescentar acidental.

Ferramentas

Modularidade, abstração, ocultação de informação, herança, composição.

Processo genérico

Perceber o problema → modelo "caixa preta" (casos de uso) → procurar soluções existentes (arquiteturas e padrões) → protótipos → documentar e rever → iterar (refactor).

Boas característicasSintomas de mau desenho
Complexidade mínima; baixo acoplamento; fácil manutenção; extensibilidade (pode chocar com simplicidade); reutilização; portabilidade; fan-in alto em utilitários e fan-out baixo a médio; leanness ("na dúvida, deixa de fora"); estratificação em camadas; técnicas padrãoRigidez (cada mudança afeta muitas partes); fragilidade (partes inesperadas partem); imobilidade (difícil reutilizar); viscosidade (o "hack" é mais fácil que manter o desenho, ou o ambiente é lento)

Níveis de abstração: estilos/padrões de arquitetura → padrões de desenho → idiomas de programação, tudo apoiado em princípios (SOLID, DRY…).

4 · GRASP: onde pôr cada responsabilidade

General Responsibility Assignment Software Patterns: orientações (não regras rígidas) para atribuir responsabilidades a classes, com vista a alta coesão e baixo acoplamento.

PrincípioRegraExemplo (loja online)
Information ExpertDar a responsabilidade à classe que tem a informação necessária para a cumprirProduct sabe o seu preço e disponibilidade; Order calcula o total das suas linhas. Risco: classes demasiado complexas (quem guarda na BD?)
CreatorB cria A se B contém/agrega A, usa A de perto ou tem os dados para o inicializarOrder cria as suas OrderLine
ControllerUma classe intermediária recebe os eventos da interface e coordena os objetos de domínioShoppingCartController
Low CouplingMinimizar dependências entre classes; comunicar por interfaces bem definidasShoppingCart não mexe nos internos de Product
High CohesionAs responsabilidades de uma classe estão relacionadas e focadas num propósitoShoppingCart não trata de pagamentos nem de autenticação
PolymorphismVariações de comportamento por tipo ⇒ métodos polimórficos, não if/switchInterface PaymentProcessor com várias implementações
Pure FabricationInventar uma classe sem correspondência no domínio para manter coesão/acoplamentoShoppingCartValidator
Indirection / Protected VariationsIntermediário para desacoplar; proteger contra variações atrás de interfaces estáveisAdapter, Facade

Tipos de acoplamento (do pior para o melhor)

Conteúdo (acede aos internos de outra) > comum (variáveis globais partilhadas) > externo (bibliotecas, APIs) > controlo (passa flags que controlam o fluxo da outra) > dados (só passa dados por parâmetros: o desejável). Há ainda o temporal (ordem de chamadas importa).

5 · Padrões de desenho: classificação

Um padrão é uma solução reutilizável para um problema recorrente: descreve problema, contexto, estrutura e consequências, não é código para copiar. Dá vocabulário comum. Usar um padrão tem sempre custos (trade-offs). O livro do Gang of Four (Gamma, Helm, Johnson, Vlissides) cataloga 23 padrões em 3 categorias:

CategoriaPreocupaçãoPadrões
CriacionaisComo criar objetos, escondendo a lógica de criaçãoSingleton, Builder, Factory Method, Abstract Factory, Prototype
EstruturaisComo compor classes e objetos em estruturas maioresAdapter, Decorator, Proxy, Composite, Facade, Bridge, Flyweight
ComportamentaisComo os objetos comunicam e distribuem responsabilidadesStrategy, Observer, Chain of Responsibility, Mediator, Template Method, Iterator, Command, State, Visitor, Memento, Interpreter
Reconhecer o padrão pelo código
  • Construtor private + static getInstance() → Singleton.
  • X.instance().a(…).b(…).build() → Builder.
  • Classe que chama métodos de outra com interface diferente (doThis() chama doThat()) → Adapter.
  • new A(new B(new C(obj))) com a mesma interface e comportamento acumulado → Decorator (ou cadeia de responsabilidade se cada um decide se trata ou passa).
  • Objeto que se passa ao sucessor quando não consegue tratar o pedido → Chain of Responsibility.
  • Algoritmo escolhido em execução através de uma interface (Comparator) → Strategy.
  • Método concreto na classe abstrata que só usa métodos abstratos → Template Method.
  • hasNext()/next() sem expor a estrutura interna → Iterator.
  • Objetos que não se conhecem e falam através de um central → Mediator.
  • Lista de "listeners" notificados quando o estado muda → Observer.

6 · Padrões criacionais

Singleton

Garante uma única instância e um ponto de acesso global. A instância só é criada quando é pedida pela primeira vez (lazy initialization: atrasar a criação até ser precisa, poupando recursos). Em multithreading: synchronized ou instância criada logo na declaração (eager).

public final class Logger {
    private static Logger instance;                 // null até ser precisa
    private Logger() { }                            // ninguém faz new de fora
    public static synchronized Logger getInstance() {
        if (instance == null) instance = new Logger();   // lazy initialization
        return instance;
    }
}

Builder

Constrói objetos complexos passo a passo com uma interface fluente, evitando construtores com muitos parâmetros.

public class Employee {
    private final String name;
    private final int department;
    private Employee(Builder b) { name = b.name; department = b.department; }
    public static Builder instance() { return new Builder(); }
    public static class Builder {
        private String name; private int department;
        public Builder name(String n)    { name = n; return this; }   // devolve this: encadear
        public Builder department(int d) { department = d; return this; }
        public Employee build()          { return new Employee(this); }   // objeto novo e imutável
    }
}
Employee e = Employee.instance().name("Henrique").department(3).build();

Factory Method e Abstract Factory

  • Factory Method: um método (muitas vezes abstrato) decide que subclasse instanciar; o cliente pede um Product sem saber a classe concreta.
  • Abstract Factory: interface para criar famílias de objetos relacionados (ex.: GUIFactory com createButton() e createCheckbox() para Windows e Mac).
  • Prototype: criar cópias de um objeto existente (clone()).

7 · Padrões estruturais

Adapter

NewApplication ──► «Wrapper / Adapter»  +doThis()  ──► LegacyComponent  +doThat()
                        doThis() { theWrappedOne.doThat(); }

Converte a interface de uma classe noutra que o cliente espera, permitindo usar componentes incompatíveis (legados, bibliotecas externas). Dois tipos de implementação:

  • Object adapter (composição): o adapter tem uma referência para o adaptado e delega. Mais flexível; funciona com subclasses do adaptado.
  • Class adapter (herança): o adapter estende o adaptado e implementa a interface alvo. Em Java só com herança simples (estende a classe e implementa a interface).

Decorator

        «interface» Component  +operation()
           ▲                     ▲
 ConcreteComponent      «abstract» Decorator ◇── component : Component
                           ▲              ▲
                    DecoratorA       DecoratorB      operation(){ component.operation(); + extra }
interface IJogador { String joga(); }
class Jogador implements IJogador {
    private final String nome; Jogador(String n) { nome = n; }
    public String joga() { return nome + " joga"; }
}
abstract class JogadorDecorator implements IJogador {
    protected final IJogador j;
    JogadorDecorator(IJogador j) { this.j = j; }
}
class Tenista extends JogadorDecorator {
    Tenista(IJogador j) { super(j); }
    public String joga() { return j.joga() + " tenis"; }
}
class Xadrezista extends JogadorDecorator {
    Xadrezista(IJogador j) { super(j); }
    public String joga() { return j.joga() + " xadrez"; }
}
// new Xadrezista(new Tenista(new Jogador("Maria"))).joga()  →  "Maria joga tenis xadrez"

Vantagens: acrescenta comportamento em tempo de execução sem alterar a classe; evita a explosão de subclasses (Tenista, Xadrezista, TenistaXadrezista…); combinações livres; respeita OCP e SRP. Desvantagens: muitos objetos pequenos; a ordem dos decoradores pode importar; difícil remover um decorador do meio.

Proxy

Substituto com a mesma interface do objeto real que controla o acesso a ele: proteção (permissões), virtual (criação preguiçosa de objeto caro), remoto, cache, logging.

Proxy vs Decorator (exame especial 2021/22)Estrutura quase igual (ambos implementam a interface e guardam uma referência). Intenção diferente: o Decorator acrescenta responsabilidades e é composto pelo cliente, muitas vezes em camadas; o Proxy controla o acesso e normalmente gere o ciclo de vida do objeto real, de forma transparente para o cliente. Ex.: BufferedReader(new FileReader(f)) é decorator; um GestorReduzido que impede eliminar é proxy.

Composite, Facade, Bridge, Flyweight

  • Composite: trata objetos individuais e composições da mesma forma (árvore parte-todo). Ex.: um Pacote que é um Servico feito de Servicos; pastas e ficheiros.
  • Facade: interface simplificada para um subsistema complexo.
  • Bridge: separa abstração e implementação para variarem de forma independente.
  • Flyweight: partilha estado comum entre muitos objetos para poupar memória.

8 · Padrões comportamentais

Strategy

Client ──► Context ◇── strategy : «interface» Strategy  +algorithm()
                                          ▲          ▲          ▲
                              ConcreteStrategyA     B          C

Família de algoritmos intermutáveis encapsulados atrás de uma interface; o contexto escolhe em execução. Ex.: algoritmos de ordenação para a lista de telemóveis (escolher o mais rápido ou o que gasta menos memória); Comparator em Collections.sort. Vantagens: trocar o algoritmo sem alterar o contexto (OCP), elimina if/switch, cada algoritmo testável isoladamente.

Context ctx = new Context(new QuickSortStrategy());
ctx.sort(phones);
ctx.setStrategy(new MergeSortStrategy());   // troca em execução
ctx.sort(phones);

Chain of Responsibility

O pedido percorre uma cadeia de handlers; cada um trata-o ou passa-o ao seguinte. O emissor não sabe quem vai tratar.

abstract class Handler {
    private Handler next;
    public Handler setNext(Handler n) { next = n; return n; }
    public void handle(String food) {
        if (canHandle(food)) cook(food);
        else if (next != null) next.handle(food);
        else System.out.println("No chef can prepare this food.");
    }
    protected abstract boolean canHandle(String food);
    protected abstract void cook(String food);
}
class PastaChef extends Handler {
    protected boolean canHandle(String f) { return f.contains("pasta"); }
    protected void cook(String f) { System.out.println("Cooking a pasta."); }
}
// h0 = Sushi → Pasta → Burger → Pizza;  order("I'd like a pizza", h0) → "Cooking a pizza."

Mediator

Um objeto central encapsula a forma como vários objetos ("colegas") interagem; eles não se referem diretamente uns aos outros (de N×N ligações para N). Ex.: torre de controlo e aeronaves; chat room; formulário que coordena os seus componentes.

«interface» Mediator ◄───── «abstract» Colleague (tem referência ao mediator)
       ▲                         ▲              ▲
   ATCTower ──conhece──►      Airplane      Helicopter
TorreControlo torre = new ATCTower();
Aviao a = new Aviao("TP101", torre);
Helicoptero h = new Helicoptero("INEM1", torre);
a.aterrar();   // TP101: autorizado a aterrar
h.aterrar();   // INEM1: aguarde, pista ocupada por TP101
a.sair();      // TP101: pista livre
h.aterrar();   // INEM1: autorizado a aterrar

Observer

«interface» Subject  +attach(o) +detach(o) +notify()  ◇──*  «interface» Observer +update()
        ▲                                                         ▲
  ConcreteSubject (estado)                                 ConcreteObserver

Dependência um-para-muitos: quando o sujeito muda, todos os observadores são notificados. Vantagens: baixo acoplamento entre sujeito e observadores, registo dinâmico, broadcast. Desvantagens: ordem de notificação imprevisível, atualizações em cascata, fugas de memória se não se fizer detach. Exemplos: listeners de GUI, subscrições de notícias, MVC (modelo notifica vistas).

Template Method

Uma classe abstrata define o esqueleto de um algoritmo num método concreto que chama passos abstratos ("hooks"); as subclasses implementam os passos sem mudar a estrutura. É o caso de AbstractList.lastIndexOf, que só usa listIterator() e size(), implementados pelas subclasses.

Iterator

Percorre os elementos de uma coleção sequencialmente sem expor a representação interna (hasNext/next, e hasPrevious/previous no ListIterator).

Outros que convém reconhecer

  • Command: encapsula um pedido num objeto (undo/redo, filas de tarefas).
  • State: o objeto muda de comportamento quando muda o estado interno (uma classe por estado).
  • Visitor: acrescenta operações a uma estrutura de objetos sem alterar as classes.
  • Memento: guarda e restaura o estado de um objeto sem violar o encapsulamento.

ATP1 2024/25 (2 de abril de 2025)

1. Low Coupling e Information Expert

Low Coupling: distribuir responsabilidades de forma a minimizar as dependências entre classes, para que uma mudança numa não obrigue a mudar as outras; facilita manutenção, reutilização e testes. Information Expert: atribuir uma responsabilidade à classe que tem a informação necessária para a cumprir (ex.: Order.getTotal() soma as suas linhas); melhora o encapsulamento e a coesão.

2. Copiar ficheiros entre dispositivos (program to an interface / DIP)
public interface Storage {
    byte[] read(File file);
    boolean write(File file, byte[] data);
}
public class UsbStorage implements Storage {
    public byte[] read(File fn) { /* ... */ }
    public boolean write(File fn, byte[] data) { /* ... */ }
}
public class CloudStorage implements Storage {
    public byte[] read(File fn) { /* ... */ }
    public boolean write(File fn, byte[] data) { /* ... */ }
}
public class TransferUtils {
    public static void copyFile(Storage from, File orig, Storage to, File dest) {   // abstrações!
        byte[] data = from.read(orig);
        // transformar, comprimir, cifrar...
        to.write(dest, data);
    }
}
A resolução que circula fica a meioCria a interface e a classe abstrata mas mantém copyFile(UsbStorage usb, …, CloudStorage ssd, …). O módulo de alto nível continua a depender das classes concretas: é precisamente o que o exercício pede para mudar. Com Storage nos parâmetros, copia-se entre quaisquer dois dispositivos, incluindo novos, sem alterar TransferUtils.
3. SomeClass com getInstance()

a) Singleton. b) Lazy initialization: a instância só é criada na primeira chamada a getInstance() (enquanto não é precisa, instance fica a null), poupando recursos se nunca for usada. Nota: esta versão não é thread-safe; usar synchronized ou inicialização na declaração.

4. Employee.instance().name(…).department(…).build()

Builder: código na secção 6. A resolução que circula guarda um único Employee dentro do builder e devolve-o em build(); funciona neste main, mas o objeto continua alterável através do builder depois de construído. A versão da secção 6 cria um objeto novo e imutável em cada build().

5. NewApplication → Wrapper → LegacyComponent

a) Adapter (wrapper). b) Os dois tipos de implementação são o object adapter (composição: o adapter tem uma referência ao LegacyComponent e delega, como no diagrama) e o class adapter (herança: o adapter estende LegacyComponent e implementa a interface que a aplicação espera). A resolução que circula dá exemplos de uso em vez de tipos de implementação.

6. Decorator: UML, exemplo e vantagens

UML, código (Jogador/Tenista/Xadrezista) e vantagens na secção 7. Saída testada: Maria joga tenis xadrez.

ATP2 2024/25 (4 de junho de 2025) e 2022/23

1. Chefs (SushiChef, PastaChef, …) — 2022/23: tradutores

a) Chain of Responsibility. O pedido (os últimos 7 caracteres) entra no 1.º handler; cada chef verifica se sabe preparar a comida; se sim prepara, senão passa ao sucessor; se nenhum souber, o último responde "No chef can prepare this food.". b) UML: Handler abstrato com -next: Handler (auto-associação) e handle(); subclasses SushiChef, PastaChef, BurgerChef, PizzaChef; o cliente conhece só o 1.º handler. Código na secção 8; a execução produz exatamente as 5 linhas do enunciado.

Em 2022/23 a mesma pergunta usava new TranslatorEN(new TranslatorES(new TranslatorPT(new TranslatorUK()))): também é Chain of Responsibility (cada tradutor trata a sua língua ou passa ao seguinte; FR não tem ninguém). Não é Strategy.

2. Mediator: problema, diagrama e main

Problema: num aeroporto, aviões e helicópteros querem aterrar mas não se conhecem; pedem à torre de controlo, que decide quem usa a pista. Diagrama e main na secção 8 (testado).

3. Collections.sort(list) → list.sort(null)

a) Strategy: o critério de comparação é uma estratégia injetável (Comparator; com null usa a ordem natural, Comparable), e o algoritmo de ordenação pode variar sem mudar o código cliente. Collections.sort também delega no método da própria lista (cada List pode ter a sua implementação). Vantagens: trocar o critério/algoritmo sem modificar o contexto, reutilização, OCP. b) UML: List (contexto) ── Comparator<T> «interface» com compare(), implementado por comparadores concretos.

4. AbstractList.lastIndexOf

a) Template Method e Iterator. b) lastIndexOf é um método concreto (esqueleto) que só usa operações abstratas: listIterator(size()) e size() são implementadas por cada subclasse (ArrayList, LinkedList…). O ListIterator percorre a lista do fim para o início com hasPrevious()/previous() sem expor a estrutura interna; quando encontra o elemento devolve nextIndex(), que é o índice do elemento acabado de visitar.

5. Arquitetura microkernel

Ver a tabela da secção 9. Resposta-tipo: núcleo com a funcionalidade mínima e um registo de plug-ins; cada plug-in é independente e liga-se ao núcleo por um contrato. Vantagens: extensibilidade, personalização, isolamento e testabilidade dos plug-ins. Desvantagens: escalabilidade e desempenho limitados pelo núcleo, contratos difíceis de evoluir. Exemplo: VS Code ou Eclipse (o editor é o núcleo; Java e Python são extensões).

2022/23 — 3. Revista de telemóveis com vários algoritmos de ordenação

Strategy: interface SortStrategy com sort(List<Phone>, Comparator), implementada por QuickSort, MergeSort, InsertionSort…; o contexto (PhoneCatalog) recebe a estratégia e pode trocá-la conforme o desempenho pretendido (tempo ou memória). interface Servico { String getNome(); String getDescricao(); double getPreco(); }

abstract class ServicoBase implements Servico {
    private final String nome, descricao;
    private final double preco;
    protected ServicoBase(String nome, String descricao, double preco) {
        this.nome = nome; this.descricao = descricao; this.preco = preco;
    }
    public String getNome() { return nome; }
    public String getDescricao() { return descricao; }
    public double getPreco() { return preco; }
    protected abstract String tipo();
    @Override public String toString() {
        return tipo() + " com nome=" + nome + ", descricao=" + descricao + ", preco=" + getPreco();
    }
}
class Internet extends ServicoBase {
    Internet(String n, String d, double p) { super(n, d, p); }
    protected String tipo() { return "Internet"; }
}
class Telefone extends ServicoBase {
    Telefone(String n, String d, double p) { super(n, d, p); }
    protected String tipo() { return "Telefone"; }
}
class Televisao extends ServicoBase {
    private final int canais;
    Televisao(String n, String d, double p, int canais) { super(n, d, p); this.canais = canais; }
    protected String tipo() { return "Televisao"; }
    @Override public String toString() { return super.toString() + ", canais=" + canais; }
}

/* b) Composite: um pacote É um Servico feito de Servicos */
class Pacote implements Servico {
    private static final double DESCONTO = 0.20;
    private final String nome, descricao;
    private final int mesesFidelizacao;
    private final List<Servico> servicos = new ArrayList<>();
    Pacote(String nome, String descricao, int meses) {
        this.nome = nome; this.descricao = descricao; this.mesesFidelizacao = meses;
    }
    public Pacote adicionar(Servico s) { servicos.add(s); return this; }
    public String getNome() { return nome; }
    public String getDescricao() { return descricao; }
    public double getPreco() {
        double total = 0;
        for (Servico s : servicos) total += s.getPreco();
        return total * (1 - DESCONTO);
    }
    @Override public String toString() {
        StringBuilder sb = new StringBuilder("Pacote com nome=" + nome + ", descricao=" + descricao
                + ", preco=" + getPreco() + " com fidelizacao de " + mesesFidelizacao + " meses");
        for (Servico s : servicos) sb.append("\n\t").append(s);
        return sb.toString();
    }
}

interface GestorServicos {
    void registarServico(String chave, Servico servico);
    boolean existeServico(String chave);
    Servico obterServico(String chave);
    Servico eliminarServico(String chave);
    Map<String, Servico> listar();
}

/* a) */
class GestorServicosStandard implements GestorServicos {
    private final Map<String, Servico> servicos = new TreeMap<>();
    public void registarServico(String chave, Servico s) { servicos.put(chave, s); }  // put substitui
    public boolean existeServico(String chave) { return servicos.containsKey(chave); }
    public Servico obterServico(String chave) { return servicos.get(chave); }
    public Servico eliminarServico(String chave) { return servicos.remove(chave); }
    public Map<String, Servico> listar() { return Collections.unmodifiableMap(servicos); }
}

/* c) Proxy de proteção */
class GestorServicosReduzidos implements GestorServicos {
    private final GestorServicos real;
    GestorServicosReduzidos(GestorServicos real) { this.real = real; }
    public void registarServico(String c, Servico s) {
        throw new UnsupportedOperationException("Registar nao permitido neste gestor");
    }
    public Servico eliminarServico(String c) {
        throw new UnsupportedOperationException("Eliminar nao permitido neste gestor");
    }
    public boolean existeServico(String c) { return real.existeServico(c); }
    public Servico obterServico(String c) { return real.obterServico(c); }
    public Map<String, Servico> listar() { return real.listar(); }
}

/* d) Singleton */
final class Logger {
    private static Logger instancia;
    private final List<String> historico = new ArrayList<>();
    private Logger() { }
    public static synchronized Logger getInstance() {
        if (instancia == null) instancia = new Logger();
        return instancia;
    }
    public void registar(String mensagem) { historico.add(mensagem); }
    public List<String> getHistorico() { return Collections.unmodifiableList(historico); }
}

/* d) Decorator: acrescenta histórico a QUALQUER gestor */
class GestorServicosHistorico implements GestorServicos {
    private final GestorServicos gestor;
    GestorServicosHistorico(GestorServicos gestor) { this.gestor = gestor; }
    public void registarServico(String c, Servico s) {
        gestor.registarServico(c, s);
        Logger.getInstance().registar("registarServico(" + c + ") -> " + s.getNome());
    }
    public Servico eliminarServico(String c) {
        Servico s = gestor.eliminarServico(c);
        Logger.getInstance().registar("eliminarServico(" + c + ") -> " + (s == null ? "inexistente" : s.getNome()));
        return s;
    }
    public boolean existeServico(String c) { return gestor.existeServico(c); }
    public Servico obterServico(String c) { return gestor.obterServico(c); }
    public Map<String, Servico> listar() { return gestor.listar(); }
}
