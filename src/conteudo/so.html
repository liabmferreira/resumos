1 · O que é um sistema operativo

Um SO é o programa que faz de intermediário entre o utilizador e o hardware. Tem dois papéis:

Gestor de recursos

Reparte CPU, memória, ficheiros e dispositivos de E/S entre programas e utilizadores, de forma eficiente e justa.

Programa de controlo

Controla a execução dos programas para evitar erros e uso indevido do computador.

O kernel é a parte que está sempre a correr. O resto são programas de sistema (vêm com o SO) e aplicações.

Interrupções

  • Os controladores de dispositivos avisam o CPU que terminaram uma operação através de uma interrupção (hardware).
  • O CPU guarda o estado, consulta o vetor de interrupções para saber qual a rotina de serviço (ISR), executa-a e retoma.
  • Uma trap (ou exceção) é uma interrupção gerada por software: erro (divisão por zero, acesso inválido) ou pedido de serviço ao SO (system call).
  • O SO é orientado a interrupções (interrupt driven).

Armazenamento e E/S

  • Hierarquia: registos → cache → memória principal (volátil) → SSD → disco → ótico/fita. Mais acima: mais rápido, mais caro, menor.
  • Caching: copiar dados para um armazenamento mais rápido enquanto são usados.
  • DMA: o controlador transfere blocos inteiros diretamente para a memória e só gera uma interrupção por bloco (não uma por byte).

Multiprogramação e multitarefa

  • Multiprogramação: vários jobs em memória; quando um espera por E/S, o CPU passa para outro. Objetivo: CPU sempre ocupado.
  • Multitarefa (time sharing): o CPU troca tão depressa entre processos que cada utilizador interage com o seu programa como se estivesse sozinho (tempo de resposta < 1 s).
  • Multiprocessador (SMP): vários CPUs partilham memória; mais throughput, economia, fiabilidade. Multicore: vários núcleos no mesmo chip.

Modo dual

Modo utilizador vs modo kernelUm bit de modo no hardware indica se o CPU está em modo utilizador (1) ou kernel (0). As instruções privilegiadas (E/S, gestão de interrupções, timer, tabelas de páginas) só correm em modo kernel. Uma system call faz uma trap que muda para modo kernel; o retorno volta a modo utilizador. O timer gera interrupções periódicas para o SO recuperar o controlo (evita que um processo fique com o CPU para sempre).

2 · Serviços, system calls e estruturas do SO

Serviços

Para o utilizador

  • Interface (CLI, GUI, toque, batch)
  • Execução de programas
  • Operações de E/S
  • Sistema de ficheiros
  • Comunicação (memória partilhada ou mensagens)
  • Deteção de erros

Para o próprio sistema

  • Alocação de recursos
  • Contabilização (logging)
  • Proteção e segurança

System calls

  • Interface de programação para os serviços do SO. Normalmente usadas através de uma API (POSIX, Win32, Java API) e não diretamente; a API é portável e esconde os detalhes.
  • A system-call interface mantém uma tabela indexada pelo número de cada chamada.
  • Passagem de parâmetros: em registos; num bloco/tabela em memória com o endereço num registo (Linux); ou na pilha.
  • Tipos: controlo de processos, gestão de ficheiros, gestão de dispositivos, informação, comunicação, proteção.

3 · Processos

ProcessoUm programa em execução. O programa é passivo (ficheiro executável); o processo é ativo. Em memória tem: text (código), data (variáveis globais), heap (memória dinâmica, cresce para cima) e stack (variáveis locais, parâmetros, endereços de retorno; cresce para baixo). Tem ainda o program counter e os registos.

PCB (Process Control Block)

Estrutura do kernel com tudo sobre o processo: estado, PID, program counter, registos, informação de escalonamento (prioridade, filas), de memória (tabela de páginas, limites), de contabilização (tempo de CPU) e de E/S (ficheiros abertos). No Linux é a task_struct.

Escalonamento de processos

  • Filas: ready queue e wait queues (uma por evento/dispositivo).
  • Troca de contexto: guardar o estado do processo atual no seu PCB e carregar o do próximo. É overhead puro (nada de útil é feito) e depende do hardware.
  • Processos I/O-bound (muitos bursts curtos de CPU) vs CPU-bound (poucos bursts longos).

Criação e terminação

ChamadaO que faz
fork()Cria um filho que é uma cópia do pai (mesmo código, cópia dos dados). Devolve 0 no filho e o PID do filho no pai (−1 em erro). Os dois continuam na instrução seguinte.
exec*()Substitui a imagem do processo por outro programa. Mantém o PID. Se tiver sucesso, nunca retorna: o código a seguir não é executado.

Terminação em cascata: alguns sistemas não deixam um filho existir se o pai terminar.

Comunicação entre processos (IPC)

  • Processos independentes ou cooperantes (partilha de informação, velocidade, modularidade).
  • Memória partilhada: rápida, mas os processos têm de se sincronizar (produtor-consumidor com buffer limitado).
  • Troca de mensagens: send/receive; direta ou por mailboxes; bloqueante (síncrona) ou não bloqueante.
  • Pipes (ordinários: pai-filho, unidirecionais; com nome/FIFO: entre processos quaisquer), sockets, RPC.

4 · Método para as perguntas de fork

Passos
  1. Dá ao processo inicial o PID 111. Percorre o código linha a linha.
  2. Em cada fork(), o processo divide-se num ramo pai (valor de retorno = PID do filho, diferente de 0) e num ramo filho (valor 0) com um PID novo (222, 333...).
  3. Num if (fork() == 0) o filho entra no if; o pai vai para o else. Com != 0 é ao contrário.
  4. Depois de um execlp bem sucedido, esse processo não executa mais nenhuma linha do programa: só imprime o que o novo programa (ex.: echo) imprimir.
  5. Conta os processos (nós da árvore) e as impressões de cada um. A ordem entre processos diferentes não está definida; dentro de um processo, a ordem é a do código, e um filho só imprime depois do fork que o criou.
Regras da ordem das saídasTudo o que um processo imprime antes de um fork aparece uma vez só (com \n e saída para terminal). O que vem depois de k forks não condicionados aparece 2k vezes. Para dar "duas saídas possíveis", troca a ordem entre o pai e o filho num ponto onde correm em paralelo.

5 · Threads

ThreadUnidade básica de utilização do CPU: tem o seu ID, program counter, registos e stack. Partilha com as outras threads do mesmo processo o código, os dados (globais), o heap e os ficheiros abertos.
Processo vs thread (saiu em 2023/24, I d)Um processo é um programa em execução com o seu próprio espaço de endereços e recursos; os processos estão isolados entre si. Uma thread é um fluxo de execução dentro de um processo; as threads do mesmo processo partilham memória e recursos, por isso criar uma thread e trocar entre threads é muito mais barato, mas o acesso a dados partilhados tem de ser sincronizado.

Benefícios

  • Responsividade: a aplicação continua a responder enquanto uma thread bloqueia.
  • Partilha de recursos: mais fácil do que memória partilhada ou mensagens.
  • Economia: criar uma thread é mais barato do que criar um processo.
  • Escalabilidade: aproveita arquiteturas multicore.

Concorrência vs paralelismo

Concorrência: várias tarefas fazem progresso (mesmo num só núcleo, intercaladas). Paralelismo: várias tarefas executam ao mesmo tempo (precisa de vários núcleos). Paralelismo de dados (o mesmo cálculo sobre partes dos dados) vs de tarefas (operações diferentes em threads diferentes).

Lei de AmdahlCom uma fração série S e N núcleos: speedup ≤ 1 / (S + (1 − S)/N). Quando N → ∞, o limite é 1/S. Ex.: 75 % paralelo (S = 0,25), 2 núcleos → 1/(0,25 + 0,375) = 1,6; 4 núcleos → 1/(0,25 + 0,1875) ≈ 2,29; máximo 4.

Threads de utilizador são geridas por uma biblioteca (POSIX Pthreads, Windows, Java); threads de kernel são geridas pelo SO.

Pthreads

#include <pthread.h>
void *runner(void *param);              /* função da thread */

pthread_t tid;                          /* identificador */
pthread_attr_t attr;
pthread_attr_init(&attr);               /* atributos por omissão */
pthread_create(&tid, &attr, runner, argumento);
pthread_join(tid, NULL);                /* espera que a thread termine */
pthread_exit(NULL);                     /* termina só a thread que a chama */
exit() vs pthread_exit()exit() (ou return do main) termina o processo inteiro, e com ele todas as threads. pthread_exit() no main termina só a thread principal; o processo continua até a última thread acabar. Esta diferença saiu no recurso de 2022/23.

Threading implícito

A criação e gestão das threads passa para compiladores e bibliotecas: thread pools (threads criadas de antemão à espera de trabalho: mais rápido e limita o número de threads), fork-join, OpenMP (#pragma omp parallel), Grand Central Dispatch, Intel TBB.

Questões

  • fork() numa thread: duplica todas as threads ou só a que chamou? (UNIX tem as duas versões.) Se a seguir vem exec(), basta duplicar a que chamou, porque o exec substitui o processo todo.
  • Sinais: entregues à thread a que se aplicam, a todas, a algumas, ou a uma thread designada.
  • Cancelamento: assíncrono (termina já) ou diferido (a thread verifica periodicamente se deve terminar, em pontos de cancelamento). O diferido é o habitual.
  • Thread-local storage (TLS): dados próprios de cada thread que persistem entre chamadas de funções (como static, mas por thread).
  • Ativações de escalonador: LWP (lightweight process) entre threads de utilizador e de kernel; upcalls do kernel para a biblioteca.

6 · Sincronização e semáforos

Condição de corrida e secção críticaHá uma condição de corrida quando o resultado depende da ordem em que threads acedem a dados partilhados. A secção crítica é o troço de código que acede a esses dados. Uma solução tem de garantir: exclusão mútua, progresso e espera limitada (sem adiamento indefinido).

Semáforo

Inteiro com duas operações atómicas:

  • down() (wait, P): decrementa; se ficar negativo (ou se já era 0), a thread bloqueia.
  • up() (signal, V): incrementa; se há threads bloqueadas, acorda uma.

Um semáforo iniciado a 1 é um mutex; iniciado a 0 serve para sinalizar ("espera até alguém fazer up").

Padrões que saem

PadrãoIdeia
Mutexmutex.down(); secção crítica; mutex.up();
Turnstile (torniquete)t.down(); t.up(); Deixa passar uma thread de cada vez; fechado por alguém que faça t.down() e não devolva.
BarreiraNinguém passa do ponto X até as N threads lá chegarem (contador protegido por mutex + semáforo a 0).
Barreira reutilizávelDuas fases: count++ abre a 1.ª porta quando chega a N; count-- abre a 2.ª quando chega a 0.
Leitores-escritoresVários leitores ao mesmo tempo, escritores sozinhos. O primeiro leitor fecha nobody, o último abre.

Variáveis de condição

Semáforos vs variáveis de condição (sai quase todos os anos)
  • O semáforo tem memória (contador): um up() sem ninguém à espera não se perde, fica guardado para o próximo down().
  • Num semáforo, down() só bloqueia se o valor for 0.
  • A variável de condição não tem estado: signal() sem threads à espera perde-se.
  • wait() bloqueia sempre e é usado com um mutex: liberta-o atomicamente ao bloquear e volta a adquiri-lo ao acordar.
  • Por isso a condição testa-se num while (while (!cond) wait(c, m);) e não num if.
  • Os semáforos servem para exclusão mútua e para sinalizar; as variáveis de condição esperam por uma condição arbitrária sobre dados protegidos por um mutex (monitores).

Deadlock

As 4 condições necessárias (Coffman)Só há deadlock se se verificarem as quatro ao mesmo tempo:
  1. Exclusão mútua: pelo menos um recurso só pode ser usado por um processo de cada vez.
  2. Posse e espera (hold and wait): um processo tem um recurso e espera por outro.
  3. Sem preempção: um recurso só é libertado voluntariamente por quem o tem.
  4. Espera circular: P0 espera por P1, P1 por P2, …, Pn por P0.
Para evitar: quebrar uma delas (ex.: ordem global na aquisição dos recursos elimina a espera circular). Outras abordagens: evitar (algoritmo do banqueiro, estado seguro), detetar e recuperar, ignorar (a maioria dos SOs).

7 · Escalonamento do CPU

  • Tempo de espera = tempo de fim − chegada − duração (tempo passado na ready queue).
  • Turnaround = fim − chegada. Resposta = primeira vez que corre − chegada.
  • Critérios: utilização do CPU e throughput (maximizar); turnaround, espera e resposta (minimizar).
AlgoritmoRegraCaracterísticas
FCFSPor ordem de chegada; não preemptivoSimples; efeito comboio (curtos esperam atrás de um longo); bom para jobs de cálculo
SJFEscolhe o menor burst; não preemptivoÓtimo no tempo médio de espera; precisa de estimar o burst (média exponencial τn+1 = α tn + (1 − α) τn); starvation dos longos
SRTF (SJF preemptivo)Quando chega um processo com burst menor do que o restante do atual, este é interrompidoAinda menor espera média; mais trocas de contexto; starvation
PrioridadesCorre o de maior prioridade (pode ser preemptivo)Starvation; resolve-se com aging

Fazer o diagrama sem errar
  1. Escreve uma tabela com o tempo restante de cada processo.
  2. Avança só até ao próximo evento: chegada, fim ou fim de quantum.
  3. Em cada evento decide quem corre (no SRTF compara restantes; no RR, quem chega no mesmo instante em que acaba um quantum entra na fila antes do que é preemptado — convenção usual).
  4. No fim calcula a espera de cada um com fim − chegada − duração e faz a média.

8 · FAT32 e memória virtual

FAT

A File Allocation Table tem uma entrada por cluster. A entrada i diz qual é o próximo cluster do ficheiro que usa o cluster i: FFFFFFFF = último cluster (fim da cadeia), 00000000 = livre. Os clusters 0 e 1 estão reservados. A entrada de diretório guarda o primeiro cluster de cada ficheiro.

Método
  1. Parte do primeiro cluster e salta: c → FAT[c] → … até FFFFFFFF. Os valores estão em hexadecimal (000A = 10, 000D = 13).
  2. Byte b de um ficheiro com clusters de T bytes: índice = ⌊b / T⌋ (a contar do 0) na cadeia; offset = b mod T.

Vantagem: acesso aleatório só lendo a FAT (que pode ficar em memória). Desvantagem: a FAT ocupa muito espaço em discos grandes e um acesso longe no ficheiro obriga a seguir a cadeia.

Paginação

  • A memória lógica de cada processo é dividida em páginas; a física em frames do mesmo tamanho. A tabela de páginas do processo diz em que frame está cada página.
  • Endereço lógico = (página p, deslocamento d); endereço físico = frame[p] × tamanho + d. Nos exames cada página tem 1 byte, por isso o endereço físico é simplesmente o número da frame.
  • TLB (Translation Lookaside Buffer): cache associativa, em hardware, das traduções página → frame mais recentes. Num TLB hit evita-se o acesso à tabela de páginas em memória (que custaria um acesso extra por cada acesso); num miss consulta-se a tabela e guarda-se a tradução na TLB.

Memória virtual

  • Só as páginas necessárias estão em memória (paginação a pedido); as outras ficam no disco (swap). Bit de validade na tabela de páginas.
  • Page fault: acesso a uma página que não está em memória → trap ao SO → verifica se o acesso é válido (senão termina o processo) → encontra uma frame livre (ou escolhe uma vítima com um algoritmo de substituição: FIFO, ótimo, LRU) → lê a página do disco → atualiza a tabela (bit válido) → repete a instrução.
  • Objetivos: transparência (cada processo vê um espaço de endereços contínuo e grande, maior do que a memória física, sem saber onde estão as páginas); proteção/segurança (cada processo só acede às suas páginas); eficiência (mais processos em memória, menos E/S ao carregar); partilha (bibliotecas e memória partilhada mapeadas em vários processos).
  • Proteção: cada processo tem a sua tabela de páginas e só consegue gerar endereços lógicos que a MMU traduz pela sua tabela; não há forma de nomear uma frame de outro processo. As tabelas só podem ser alteradas em modo kernel (instruções privilegiadas), o registo base da tabela muda na troca de contexto, e há bits de proteção (leitura/escrita/execução, válido) verificados pelo hardware em cada acesso.
  • Thrashing: o processo passa mais tempo a tratar page faults do que a executar (não tem frames suficientes para o seu conjunto de trabalho).

a) Onde bloqueiam as 3 primeiras

As três primeiras fazem count++ (1, 2, 3), não entram no if, libertam o mutex e bloqueiam na linha 10 (barrier.down(), valor 0). A quarta põe count = 4, faz 4 ups: os três primeiros acordam uma thread bloqueada cada um, o quarto deixa barrier = 1. Põe count = 0, liberta o mutex e na linha 10 consome esse último up (barrier = 0) e passa. Valores finais: count = 0, mutex = 1, barrier = 0.

b) Porque falha se as threads voltarem ao início

Uma thread que é a 4.ª a chegar pode ser interrompida entre a linha 9 e a 10. As outras três acordam, fazem codeAfter(), voltam ao início e chegam outra vez à barreira (count = 1, 2, 3). Entretanto pode haver ups "sobrantes": por exemplo, se a 4.ª ainda não fez o seu down, há 1 up guardado; uma thread rápida da ronda seguinte consome-o e passa a barreira sozinha, antes de as outras chegarem. Também uma thread rápida pode apanhar um up destinado a uma thread da ronda anterior que ainda não acordou. A barreira só funciona uma vez.

    for (i = 0; i < 4; i++) barrier2.up();   /* abre a 2.ª porta */
mutex.up();
barrier2.down();
/* volta ao início */

Uma thread rápida não pode entrar na ronda seguinte antes de todas terem passado a 1.ª porta, porque fica presa em barrier2 até as 4 terem feito count--. E não pode voltar à 1.ª porta antes de todas passarem a 2.ª, porque precisa de count = 4 outra vez. Cada porta tem exatamente 4 ups para 4 downs.

d) up/down vs signal/wait

Ver a caixa "Semáforos vs variáveis de condição" na secção 6: o semáforo guarda os ups (contador), down só bloqueia a 0; a variável de condição não guarda nada, signal sem ninguém à espera perde-se, e wait bloqueia sempre e liberta o mutex associado.

a) T1 a ler; T2 leitor; T3 e T4 escritores

T1 é o 1.º leitor: readers = 1 e nobody = 0. T2 (leitor) faz mutex.down, vê readers ≠ 0, passa a readers = 2, liberta o mutex e lê ao mesmo tempo que T1. T3 e T4 bloqueiam em nobody.down() (linha 2 dos escritores). Quando T1 termina, readers = 1 (nada acontece). Quando T2 termina, readers = 0 e faz nobody.up(), que acorda T3; T3 escreve e faz nobody.up(), que acorda T4; T4 escreve e deixa nobody = 1.

b) Adiamento indefinido dos escritores e correção

Enquanto houver sempre pelo menos um leitor a ler, readers nunca chega a 0 e nobody nunca é libertado: novos leitores entram sempre e o escritor espera para sempre. Correção com um turnstile (iniciado a 1): o escritor fecha-o enquanto espera, e novos leitores ficam presos nele.

/* leitores */                     /* escritores */

mutex.down();                      WRITE_access();

readers++;                         nobody.up();
mutex.up();
READ_access();
mutex.down();
readers--;
if (readers == 0) nobody.up();
mutex.up();

Os leitores que já estavam a ler acabam, o último liberta nobody e o escritor entra. Os leitores novos só passam o turnstile quando o escritor o reabre.

/* TAREFA 3b: protótipo */
int compare_papers(const void *, const void *);

/* TAREFA 1 */
FILE *fp = fopen(argv[optind], "r");
if (fp == NULL) { printf("Erro a abrir %s\n", argv[optind]); return EXIT_FAILURE; }
char line[MAXLEN]; int N = 0;
while (fgets(line, MAXLEN, fp) != NULL) {
    N++;
    if (line[0] == '\n') { printf("Erro: linha %d vazia\n", N); fclose(fp); return EXIT_FAILURE; }
    if (line[strlen(line) - 1] != '\n') {
        printf("Erro: linha %d demasiado longa\n", N); fclose(fp); return EXIT_FAILURE;
    }
}
if (N == 0 || N % 3 != 0) { printf("Erro: %d linhas não é múltiplo de 3\n", N); fclose(fp); return EXIT_FAILURE; }

/* TAREFA 2a */
int P = N / 3;
paper *art = malloc(P * sizeof(paper));
if (art == NULL) { fclose(fp); return EXIT_FAILURE; }
rewind(fp);
for (int i = 0; i < P; i++) {
    if (fscanf(fp, " %d", &art[i].paper_id) != 1) {
        art[i].paper_id = -1;
        printf("Aviso: artigo %d (linha %d) sem número\n", i + 1, 3 * i + 1);
    }
    fscanf(fp, " %[^\n]", art[i].title);
    fscanf(fp, " %[^\n]", art[i].author);
    fscanf(fp, " %[^\n]", line);
    art[i].eval = av_score(line);
}
fclose(fp);

/* TAREFA 3a */
qsort(art, P, sizeof(paper), compare_papers);
int k = (int) ceil(percen * P - 1e-9);     /* nº mínimo de aceites por -p (precisa de math.h, -lm) */
if (k < 1) k = 1;
if (k > P) k = P;
double corte = art[k - 1].eval;            /* empatados com o k-ésimo também entram */
int nA = 0;
for (int i = 0; i < P; i++) {
    art[i].status = (art[i].eval >= limiar && art[i].eval >= corte) ? 'A' : 'R';
    if (art[i].status == 'A') nA++;
}

/* TAREFA 4a */

/* TAREFA 2b */
double av_score(char *ptr) {
    char *fim; double soma = 0; int n = 0;
    while (1) {
        double v = strtod(ptr, &fim);
        if (fim == ptr) break;             /* fim da string ou parte inválida */
        soma += v; n++; ptr = fim;
    }
    return n > 0 ? soma / n : 0.0;
}

/* TAREFA 3b: ordem decrescente de eval */
int compare_papers(const void *a, const void *b) {
    double ea = ((const paper *) a)->eval, eb = ((const paper *) b)->eval;
    return (ea < eb) - (ea > eb);
}

/* TAREFA 4b */
void print_paper(paper *p) {
    printf("%d - \"%s\" by %s\n", p->paper_id, p->title, p->author);
    printf("Score: %.2f - %s\n", p->eval, p->status == 'A' ? "ACCEPTED" : "REJECTED");
}

Teste com o exemplo do enunciado (evals 4,5 / 4 / 3,6 / 3 / 3 / 3 / 2 / 1,5): -p 0.5 -l 2.5 aceita 6; -p 0.3 aceita 3; -l 4 aceita 2. O ficheiro binário tem 6 × 224 bytes no primeiro caso.

Diferenças em relação à resolução do professor
  • O professor usa eval > limiar; o enunciado diz "igual ou superior", por isso deve ser >=.
  • O professor usa pivot = (int)(percen*P - 1), que trunca: com 8 artigos e -p 0.3 aceita só 2 (25 %). Arredondar para cima garante pelo menos a percentagem pedida. Ambas as leituras são defensáveis; diz qual usaste.
  • O ciclo final do professor, while (artigos[i].status == 'A'), lê fora do array se todos forem aceites. Contar os aceites e fazer um só fwrite evita isso.
