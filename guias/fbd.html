1 · Sistemas de gestão de bases de dadosestudado ✓

Uma BD é uma coleção organizada de dados relacionados, partilhados por várias aplicações. Um SGBD é o software que permite definir (tipos, estruturas, restrições, no catálogo), construir, manipular e partilhar BDs. Evolução: processamento isolado → sistema de ficheiros partilhados (problemas de concorrência, integridade, segurança) → SGBD.

Vantagens do SGBD

  • Independência programas/dados
  • Integridade e consistência (mesmo com falhas)
  • Eficiência, concorrência, isolamento
  • Segurança, backup e recuperação
  • Linguagem própria (SQL)

Metadados

O SGBD guarda a descrição da própria BD: tabelas, utilizadores, regras, vistas, índices, locks, esquemas.

Arquitetura ANSI/SPARC (3 níveis)

NívelDescrevePara quem
ExternoVistas adaptadas a cada utilizadorUtilizadores finais
ConceptualEntidades, tipos, relações, restrições (ex.: CREATE TABLE)Administradores e programadores
InternoImplementação física: ficheiros, páginas, índicesProgramadores de sistemas
Independência dos dados: são DOIS níveis, não trêsFísica: mudar o nível interno não afeta o conceptual. Lógica: mudar o esquema conceptual não afeta os esquemas externos nem as aplicações. (Afirmação "existem 3 níveis de independência" é falsa: há 3 níveis de arquitetura.)

Modelos de dados

  • 1.ª geração: hierárquico (árvore pai-filho 1:N; bom para acesso sequencial, mau para aleatório; não suporta N:M sem duplicar dados) e rede (grafos, registos em vários conjuntos).
  • 2.ª geração: relacional (o mais usado: bancos, hospitais, finanças).
  • 3.ª geração: objeto-relacional, OO, NoSQL (chave-valor, documentos, colunas, grafos).

2 · Desenho conceptual: modelo Entidade/Relacionamentoestudado ✓

Fases do desenho: análise de requisitos (texto) → desenho conceptual (DER, independente do SGBD) → esquema lógico (relacional, dependente do SGBD) → esquema físico. A modelação não é determinística: há vários DER válidos para o mesmo problema.

ElementoDesenho (Chen)Notas
Entidade forteRetânguloTem atributo(s) chave, sublinhados
Entidade fracaRetângulo duploNão tem chave própria; identifica-se pela entidade dona + chave parcial (sublinhado tracejado), através de um relacionamento identificador (losango duplo)
AtributoOvalDerivado (tracejado, ex.: idade), multivalor (oval duplo, ex.: ações de formação), composto (oval com sub-ovais, ex.: morada)
RelacionamentoLosangoPode ter atributos (ex.: Hours em WORKS_ON)

Classificação dos relacionamentos

  • Grau: unário (recursivo), binário (o mais comum), ternário (pode converter-se em binários).
  • Recursivo assimétrico (ex.: supervisiona): obriga a indicar os papéis (supervisor / supervisionado).
  • Cardinalidade: 1:1, 1:N, N:M.
  • Participação: total (linha dupla, cada instância participa pelo menos uma vez) ou parcial. Notação alternativa (min,max): min 0 = opcional, 1 = obrigatório.
Ler a cardinalidade na notação de ChenO número escrito junto a uma entidade diz com quantas instâncias dessa entidade se relaciona uma instância da outra. "Um funcionário trabalha num departamento; um departamento tem vários funcionários": N do lado do Funcionário, 1 do lado do Departamento. A participação marca-se em cada lado: Funcionário total (todos trabalham num departamento), Departamento total ou parcial conforme o enunciado.

Especialização e agregação

  • IS-A (superclasse/subclasses). Disjunta (d): cada entidade está em no máximo uma subclasse. Sobreposta (o): pode estar em várias. Total (linha dupla): tem de estar em pelo menos uma. Não confundir: disjunta não obriga a pertencer a uma subclasse.
  • Agregação: tratar um relacionamento como entidade para o relacionar com outra entidade.

Restrições de integridade no DER

Atributo com um só valor; chaves únicas; obrigatoriedade de valor; domínios (>, <, not null); cardinalidade; participação.

Chaves

  • Superchave: conjunto de atributos que identifica univocamente cada tuplo. O conjunto de todos os atributos é sempre superchave.
  • Chave candidata: superchave mínima (não se pode tirar nenhum atributo).
  • Chave primária: a candidata escolhida (preferir simples, estável, sem NULL).
  • Chave única (UNIQUE): outra candidata; pode ter NULL (no SQL Server, um só NULL).
  • Chave estrangeira: referencia a PK (ou UNIQUE) de outra tabela ou da própria (ex.: Super_ssn). Tem de ter o mesmo tipo. Pode ser NULL se não tiver NOT NULL. Uma tabela pode ter várias FK para a mesma tabela (ex.: Voo com origem e destino → Aeroporto). Cada FK referencia uma só tabela.

Integridade de entidade: PK nunca é NULL. Integridade referencial: o valor da FK existe na tabela referenciada ou é NULL.

Regras de Codd (as ideias)

Toda a informação está em tabelas; cada valor acessível por tabela + PK + coluna; NULL tratado de forma sistemática; catálogo também é relacional; uma linguagem completa (SQL); vistas atualizáveis quando teoricamente possível; operações sobre conjuntos; independência física e lógica; integridade definida no catálogo.

4 · SQL DDL: criar e alterar tabelasestudado ✓

CREATE TABLE EMPLOYEE (
    Fname     VARCHAR(15)   NOT NULL,
    Ssn       CHAR(9)       NOT NULL,
    Salary    DECIMAL(10,2) DEFAULT 0 CHECK (Salary > 0),
    Super_ssn CHAR(9),
    Dno       INT           NOT NULL DEFAULT 1,
    CONSTRAINT EMPPK PRIMARY KEY (Ssn),
    CONSTRAINT EMPSUPERFK FOREIGN KEY (Super_ssn) REFERENCES EMPLOYEE(Ssn)
        ON DELETE SET NULL ON UPDATE CASCADE,
    CONSTRAINT EMPDEPTFK FOREIGN KEY (Dno) REFERENCES DEPARTMENT(Dnumber)
        ON DELETE SET DEFAULT ON UPDATE CASCADE
);
ALTER TABLE EMPLOYEE ADD Job VARCHAR(12);                 -- coluna nova fica a NULL
ALTER TABLE EMPLOYEE DROP COLUMN Job;
ALTER TABLE DEPARTMENT ADD CONSTRAINT DEPMGRFK
    FOREIGN KEY (Mgr_ssn) REFERENCES EMPLOYEE(Ssn);
DROP TABLE EMPLOYEE;                                      -- falha se for referenciada
Ações referenciaisQuando o tuplo referenciado é apagado/alterado: NO ACTION (por omissão, rejeita), CASCADE (propaga), SET NULL, SET DEFAULT.
Armadilhas dos V/F
  • ALTER TABLE EMPLOYEE ADD noFiscal CHAR(9) NOT NULL; numa tabela com linhas dá erro: as linhas existentes ficariam com NULL. Só funciona com DEFAULT.
  • Não se pode criar uma tabela com FK para uma tabela que ainda não existe. Cria-se primeiro e acrescenta-se a FK depois com ALTER TABLE (é o caso de EMPLOYEE ↔ DEPARTMENT, que se referenciam mutuamente).
  • FOREIGN KEY (at1, at2) REFERENCES Y(atI) AND Z(atII) não existe: uma FK referencia uma única tabela.

No SQL Server: CREATE DATABASE, CREATE SCHEMA (agrupa objetos, ex.: dbo), tipos definidos pelo utilizador (CREATE TYPE SSN FROM CHAR(9)), IDENTITY para numeração automática.

Padrões que saem sempre

Supervisor de cada funcionário:
  π E.Fname,E.Lname,S.Fname,S.Lname ( ρE(EMPLOYEE) ⋈ E.Super_ssn=S.Ssn ρS(EMPLOYEE) )

6 · SQL DMLestudado ✓

INSERT INTO EMPLOYEE (Fname, Lname, Ssn, Dno) VALUES ('Ana', 'Silva', '123456789', 4);
UPDATE EMPLOYEE SET Salary = Salary * 1.1 WHERE Dno = 5;
DELETE FROM EMPLOYEE WHERE Dno = 5;            -- sem WHERE apaga tudo

Ordem lógica de uma consulta

SELECT   Dno, COUNT(*) AS N, AVG(Salary)   -- 5. o que mostrar (aqui nasce o alias)
FROM     EMPLOYEE                           -- 1. de onde
WHERE    Sex = 'F'                          -- 2. filtra linhas
GROUP BY Dno                                -- 3. agrupa
HAVING   COUNT(*) > 3                       -- 4. filtra grupos
ORDER BY N DESC;                            -- 6. ordena (já pode usar o alias)
Regras que caem nos V/F
  • No SELECT de uma consulta com GROUP BY só podem aparecer atributos de agrupamento ou funções de agregação. SELECT Fname, COUNT(*) FROM EMPLOYEE GROUP BY Lname está errado.
  • O alias do SELECT não pode ser usado no WHERE nem no HAVING (no SQL Server): estes são avaliados antes do SELECT. Escreve HAVING SUM(area) < 3000000, não HAVING tarea < ….
  • Condições sobre agregados vão para o HAVING, nunca para o WHERE.
  • COUNT(*) conta linhas; COUNT(col) ignora NULL; COUNT() e SUM(*) não existem.
  • Qualquer operação com NULL dá NULL (5 + NULL). Compara-se com IS NULL / IS NOT NULL, nunca com = NULL.
  • SELECT ALL (omissão) mantém duplicados; DISTINCT remove-os. UNION remove duplicados; UNION ALL não.

Junções

-- funcionário e o seu supervisor (auto-junção)
SELECT E.Lname AS Employee, S.Lname AS Supervisor
FROM EMPLOYEE AS E LEFT OUTER JOIN EMPLOYEE AS S ON E.Super_ssn = S.Ssn;

-- total de horas por funcionário, incluindo quem não tem projetos
SELECT Ssn, Fname, Lname, SUM(Hours)
FROM EMPLOYEE LEFT OUTER JOIN WORKS_ON ON Ssn = Essn
GROUP BY Ssn, Fname, Lname;

Subconsultas

-- IN / NOT IN
SELECT Fname FROM EMPLOYEE WHERE Ssn NOT IN (SELECT Essn FROM DEPENDENT);
-- EXISTS correlacionado: trabalham EXCLUSIVAMENTE em projetos do departamento 4
SELECT Fname FROM EMPLOYEE
WHERE NOT EXISTS (SELECT * FROM WORKS_ON JOIN PROJECT ON Pno = Pnumber
                  WHERE Essn = Ssn AND Dnum <> 4);
-- ALL / ANY: o país menos populoso de cada região
SELECT region, name, population FROM country AS x
WHERE population <= ALL (SELECT population FROM country AS y
                         WHERE y.region = x.region AND population > 0);
-- subconsulta no FROM (tabela derivada)
SELECT D.Dname, T.N FROM DEPARTMENT D
JOIN (SELECT Dno, COUNT(*) AS N FROM EMPLOYEE GROUP BY Dno) AS T ON T.Dno = D.Dnumber;

Outros: BETWEEN a AND b, LIKE 'A%' (% qualquer sequência, _ um carácter), IN ('Poland', 'Germany'), ORDER BY … ASC|DESC, TOP n.

7 · Vistas (views)estudado ✓

Uma vista é uma tabela virtual definida por um SELECT. Não guarda dados (salvo vistas materializadas/indexadas): o SGBD faz query modification, substituindo a vista pela sua definição.

CREATE VIEW EMPLOYEE_DEP5 AS
    SELECT Fname, Lname, Ssn, Dno FROM EMPLOYEE WHERE Dno = 5
    WITH CHECK OPTION;          -- impede inserir/alterar linhas que saiam da vista
ALTER VIEW … ; DROP VIEW EMPLOYEE_DEP5;
  • Usos: simplificar consultas, segurança (mostrar só algumas colunas), independência lógica.
  • É atualizável se for sobre uma tabela, sem agregação nem DISTINCT e incluindo as colunas obrigatórias. Vistas com GROUP BY ou várias tabelas, em geral, não são.
  • Vistas não têm parâmetros. Para isso usa-se uma UDF inline table-valued.

8 · Dependências funcionais e formas normaisestudado ✓

Objetivo: evitar redundância e anomalias de inserção, alteração e eliminação. A redundância está associada a dependências funcionais indesejadas.

Dependência funcional X → YDois tuplos com o mesmo X têm sempre o mesmo Y. É uma propriedade do esquema (semântica dos dados), não se deduz de uma instância concreta (uma instância só pode mostrar que uma DF não existe). Total (plena): Y depende de toda a chave. Parcial: depende de parte de uma chave composta. Transitiva: chave → X → Y com X não-chave.
Forma normalCondiçãoComo corrigir
1FNAtributos atómicos: sem multivalor nem relações embutidasTirar o grupo repetido para outra relação
2FN1FN e nenhum atributo não-chave depende de parte de uma chave candidata (sem DF parciais). Com chaves simples, está automaticamente em 2FNSeparar a DF parcial
3FN2FN e nenhum atributo não-chave depende transitivamente da chave (não há DF entre atributos não-chave)Separar a DF transitiva
BCNFPara toda a DF não trivial X → Y, X é superchaveDecompor; pode perder DF
4FNBCNF e sem dependências multivalor não triviais (X ↠ Y)Separar cada multivalor
Exemplo (ATP2 2023/24)

R = {A,B,C,D,E,F,G,H,I} com {A,B} → {D,F,G,I}, {B} → {C}, {D,F} → {E}, {G} → {H}.

  • Chave: {A, B} (o fecho de AB é tudo; B sozinho não chega).
  • {B} → {C} é parcial (não transitiva). {D,F} → {E} e {G} → {H} são transitivas.
  • {A,B} → {D,F,G,I} é total. R está em 1FN (sem multivalor).
  • Decompor em R1 = {A,B,C,D,F,G,I}, R2 = {D,F,E}, R3 = {G,H} não deixa tudo em 3FN: R1 ainda tem B → C (parcial, nem 2FN). Correto: {A,B,D,F,G,I}, {B,C}, {D,F,E}, {G,H}.

9 · Índices e otimizaçãoestudado ✓

  • Índice primário/ordenado: sobre o campo de ordenação do ficheiro. Clustering: sobre campo de ordenação não chave. Secundário: sobre outro campo.
  • Multinível e árvores B/B+: árvores de pesquisa sempre equilibradas, nós = páginas de disco. Procura O(log n).
  • CREATE INDEX idxEmpName ON EMPLOYEE(Fname, Minit, Lname); Um índice composto só ajuda (seek) se a pesquisa usar o primeiro atributo (prefixo à esquerda).

SQL Server

ClusteredNon-clustered

FolhasAs próprias linhas da tabelaChave + apontador (chave do clustered, ou RowID se for heap)

  • Heap: tabela sem índice clustered; as linhas não têm ordem física. Pode ter índices non-clustered.
  • UNIQUE e PRIMARY KEY criam índices automaticamente.
  • Fill factor: % de cada página preenchida na criação. Deixar espaço livre (ex.: 85 %) reduz page splits quando há inserções no meio. Para chaves sempre crescentes (identity) usa-se ≈ 100 %, pois as inserções vão sempre para o fim.
  • Filtered index: só para um subconjunto (WHERE no índice), útil para colunas esparsas.
  • Índices aceleram leituras mas atrasam INSERT/UPDATE/DELETE (têm de ser atualizados). Escolher pelos padrões de consulta: a tabela de custos do caso de estudo (sem índice / índice em star / em movie / ambos) mostra que a melhor escolha depende da fração de consultas e inserções.
  • Fragmentação: ALTER INDEX … REORGANIZE (leve) ou REBUILD WITH (FILLFACTOR = 98).

10 · Programação em T-SQLestudado ✓

Batches e scripts

  • Batch: grupo de instruções enviado de uma vez, terminado por GO (que não vai para o servidor; GO n repete n vezes).
  • Erro de sintaxe faz falhar a batch inteira; erro de runtime não anula as instruções anteriores da batch. Uma batch não é uma transação.
  • No fim da batch são destruídas as variáveis locais, tabelas temporárias e cursores criados nela. CREATE PROCEDURE/VIEW/TRIGGER têm de ser a única instrução da batch.
DECLARE @x INT = 5, @nome VARCHAR(20);
SET @x += 1;
SELECT @nome = Fname FROM EMPLOYEE WHERE Ssn = '123456789';   -- se vierem várias, fica a última
IF EXISTS (SELECT * FROM EMPLOYEE WHERE Dno = 5) PRINT 'Há' ELSE PRINT 'Não há';
WHILE @x < 10 BEGIN SET @x += 1; IF @x = 8 BREAK; END;

Cursores (5 passos)

DECLARE C CURSOR FAST_FORWARD FOR SELECT Essn, Hours FROM WORKS_ON;
OPEN C;
FETCH NEXT FROM C INTO @essn, @h;
WHILE @@FETCH_STATUS = 0          -- 0 ok, -1 fim, -2 tuplo indisponível
BEGIN
    -- processar a linha
    FETCH NEXT FROM C INTO @essn, @h;
END
CLOSE C;
DEALLOCATE C;

Percorrem os tuplos um a um ("pesca à linha"). Soluções set-based ("pesca com rede") são em geral muito mais rápidas.

Stored procedures vs UDF

Stored procedureUser defined function
Devolve 0, 1 ou vários valores; parâmetros OUTPUT; RETURN n (inteiro de estado)Devolve um escalar ou uma tabela; só parâmetros de entrada
Não pode ser usado no FROM/WHEREPode ser usada em SELECT/WHERE/HAVING (e escalar até em CHECK)
Pode alterar dados, usar TRY/CATCH, transações, chamar SPsNão altera dados, sem TRY/CATCH nem RAISERROR, sem transações, sem funções não determinísticas

Tipos de UDF: escalar; inline table-valued (RETURNS TABLE AS RETURN (SELECT …), uma "vista com parâmetros"); multi-statement table-valued (RETURNS @t TABLE (…), preenche e devolve). Invocação com o schema: dbo.fsMultiply(3, 4).

CREATE PROC dbo.GetProductName (@Code CHAR(10), @Name VARCHAR(25) OUTPUT) AS
    SELECT @Name = ProductName FROM dbo.Product WHERE Code = @Code;
GO
DECLARE @n VARCHAR(25);
EXEC dbo.GetProductName '1001', @n OUTPUT;

Erros

  • @@ERROR: código de erro da última instrução (0 = sucesso; a seguinte já repõe). @@ROWCOUNT: linhas afetadas.
  • RAISERROR('msg', severidade, estado) devolve um erro ao cliente; não faz rollback sozinho.
  • BEGIN TRY … END TRY BEGIN CATCH … END CATCH com ERROR_NUMBER(), ERROR_MESSAGE()… O erro passa o controlo para o CATCH; o rollback só acontece se o CATCH o fizer (ou com SET XACT_ABORT ON).

Triggers DML

  • Disparam uma vez por instrução (não por tuplo, ao contrário do Oracle). Devem estar preparados para várias linhas em inserted/deleted.
  • Tabelas lógicas só de leitura: inserted (novas linhas: INSERT, UPDATE) e deleted (linhas antigas: DELETE, UPDATE). Num AFTER DELETE, inserted está vazia. SPs chamados pelo trigger não as veem.
  • AFTER: vários por tabela; corre depois de todas as restrições (PK, CHECK, FK) e da escrita, antes do commit; pode fazer ROLLBACK TRAN. Não pode corrigir dados que violem restrições (a instrução já falhou antes).
  • INSTEAD OF: um por tabela/vista; substitui a instrução (que não é executada); usa-se quando é provável que a instrução falhe e se quer outra lógica (ex.: atualizar uma vista não atualizável, arquivar em vez de apagar). Não é recursivo.
  • UPDATE(coluna) diz se a coluna foi alterada.

Estados: ativa → parcialmente efetivada (executou a última instrução, mas o commit ainda não está garantido em disco) → efetivada (committed); ou ativa → falhada → abortada.

Problemas de concorrência

Atualização perdida (duas escrevem por cima), leitura suja (ler dados não efetivados de outra que depois faz rollback), leitura não repetível, fantasmas. Transações só de leitura não entram em conflito entre si.

Preventivos (pessimistas)

  • Locking: lock de leitura (partilhado) / escrita (exclusivo), libertados no commit/rollback; podem causar deadlock e esperas.
  • Etiquetagem (timestamps): ordem de chegada; conflito ⇒ desfaz e reinicia.

Otimistas

Assumem que conflitos são raros: executam livremente e validam no fim; se houver conflito, a transação é abortada e reiniciada (não há só atrasos).

Escalonamentos

  • Serializável: equivalente a uma execução em série.
  • Recuperável: nenhuma transação T faz commit antes de todas as transações de que leu dados terem feito commit.
  • Sem abort em cascata: só se lê dados já efetivados.
  • Estrito: não se lê nem escreve um elemento escrito por uma transação ainda não terminada.

Recuperação de falhas

  • O transaction log regista todas as operações (incluindo o commit) com a before-image (antes) e a after-image (depois). O log vai para disco antes dos dados (write-ahead).
  • Falha de transação: rollback com as before-images.
  • Falha de sistema: rollback com before-images + rollforward com after-images.
  • Falha de disco: restore do último backup + rollforward com as after-images.
  • Checkpoint: momento em que o log e a BD em disco ficam sincronizados; limita até onde é preciso recuar. O log não se apaga depois de cada commit (é truncado após backups/checkpoints, conforme o modelo de recuperação).
  • Savepoint: permite rollback parcial dentro de uma transação.
BEGIN TRAN;
    INSERT INTO People VALUES ('Tom');
    SAVE TRAN Savepoint1;
    INSERT INTO People VALUES ('Dick');
    ROLLBACK TRAN Savepoint1;        -- só desfaz o Dick
COMMIT TRAN;                         -- Tom fica
-- @@TRANCOUNT = nº de transações abertas

12 · Segurança no SQL Serverestudado ✓

  • Login (nível do servidor) e user (nível de cada BD). Um login pode ter um user em cada BD, mapeados para ele: CREATE USER joao_db FOR LOGIN joao;
  • Server roles (sysadmin…) e database roles fixas (db_owner, db_datareader, db_datawriter…) ou definidas pelo utilizador. Um user pode pertencer a várias roles: EXEC sp_addrolemember 'db_owner', 'joao_db';
  • GRANT SELECT, UPDATE ON Project TO MyRole [WITH GRANT OPTION]; REVOKE retira um GRANT (ou DENY). DENY proíbe explicitamente e sobrepõe-se a GRANT (incluindo os herdados de roles).
  • Ownership chaining: se o SP e as tabelas têm o mesmo dono, basta dar EXECUTE no SP para o utilizador usar as tabelas através dele.
  • Cifragem de atributos: EncryptByPassPhrase/DecryptByPassPhrase guardam dados cifrados (VARBINARY); a frase-passe deve ficar fora da BD.

31. Stored procedure TransferEmployeeDepartment

O que faz o procedimento
  1. Abre uma transação dentro de TRY.
  2. Se o funcionário não existe → erro e rollback. Se o departamento não existe → erro e rollback.
  3. Se o funcionário gere outro departamento que não o novo → erro e rollback.
  4. Muda o Dno, apaga todas as linhas de WORKS_ON do funcionário.
  5. Percorre com um cursor a lista de projetos recebida como parâmetro tabela (READONLY); se algum projeto não existe → erro e rollback; senão insere com 0 horas.
  6. Commit. No CATCH: RAISERROR e rollback.

Pormenor: quando sai pelo RETURN dentro do ciclo, o cursor fica por fechar e libertar.

Afirmações verdadeiras: valida a existência de funcionários e departamentos; usa um cursor para iterar sobre a lista passada como parâmetro de valor de tabela; insere 0 horas; gera um erro se um projeto da lista não existir. As restantes são falsas (apaga as atribuições antigas, não ignora projetos inválidos, não aceita horas negativas, não usa ERROR_MESSAGE, não verifica se já trabalhava nos projetos, só transfere um funcionário para um departamento). O próprio enunciado avisa que talvez não haja 5 certas; só encontrámos 4 defensáveis.
